Learner model, event log and data platform

Where everything known about a learner lives: one append-only event log, nine derived stores that can be rebuilt, and versioned briefs.

Reviewed twice, not revised. Both reviews found real problems that are not fixed in the text yet. Read the findings below before relying on a section.

In one paragraph

The learner model is one append-only table of events and nine derived tables that any engineer can drop and rebuild from the events in under a minute per learner. Nothing a model says is written directly: the after-session pass hands this domain a fixed-schema result, code validates it (every life fact's quote must exist word for word in a verbatim transcript or chat message), applies it in one transaction, and bumps a per-learner integer learner_model_version. Every brief a role reads, every model call and every claim shown carries that integer, so a bad episode can be traced to exactly the model state that produced it. The scheduler is the open FSRS algorithm (py-fsrs) with a 0.85 recall threshold at the next drop time; word knowledge is a Beta distribution per word and surface, so every number has a range for free. Audio lives in S3 under per-learner keys at predictable paths; text lives in Postgres with row-level security; export is a zip built from the same tables; deletion is a row-ordered purge plus key destruction, with the 30-day backup window stated as a fact of RDS retention, not a promise we have to engineer.

The decisions

Section 1's table, one card per decision. "Rejected" is what was considered and turned down.

  1. D1

    Event store

    One events table, append-only (no UPDATE/DELETE grant, trigger guard), range-partitioned by month on occurred_at, per-learner ordering by (occurred_at, seq) [DECISION, PRD-v2 8.1, 8.2]

    Why One table is what a two-person team can operate; month partitions give retention and backup granularity the topology already asked for

    Rejected Kafka or a stream (nothing consumes in real time except the after-pass, which Inngest already triggers); hash partitions by learner (no query gains over the btree at under 100M rows)

  2. D2

    Verbatim enrichment of call turns

    Two event types, call_turn (streaming, from the worker) and call_turn_verbatim (batch, from call/verbatim-turn), joined by (call_id, turn_index) in a view [DECISION]

    Why Keeps the table append-only; the topology's "update the call_turn event" becomes an append

    Rejected Updating the call_turn row (breaks D1); one event written only after verbatim (notes would wait for the whole call)

  3. D3

    Idempotency

    Client-minted UUIDv7 event_id; unique (learner_id, event_id); duplicates are ignored, not errors [DECISION]

    Why The PWA replays a 24 h offline queue; the worker retries; Inngest retries steps

    Rejected Server-assigned ids (replay would double-count)

  4. D4

    Learner-model version

    Integer per learner, bumped by one in every store-writing transaction, recorded in learner_model_versions with the cause, the event high-water mark and the code versions that wrote it; serialized as lm_v_{n} in events and traces [DECISION]

    Why The topology's CallMeta carries an int; the pipeline carries a string; both map to this

    Rejected A global version (cannot tell which learner changed); a hash of the stores (not comparable, not ordered)

  5. D5

    Who may write stores

    workflows (after-session pass, rebuilds, retention) and, for learner-authored edits only, api synchronously inside the event append transaction [DECISION, PRD-v2 8.4.7 "fixed at once"]

    Why A learner's correction must be true before the next screen renders; it is still an event, so a rebuild reproduces it

    Rejected Learner edits through Inngest (a visible delay on "my mistake, noted"); models writing anything (PRD-v2 8.1 forbids)

  6. D6

    Word knowledge

    word_bank row per (learner, unit) with Beta(α, β) per surface (ear, eye, produced); prior from frequency rank and the word-check size estimate; ranges are the Beta 10 to 90% interval [DECISION, PRD-v2 8.3]

    Why Gives p(understood) for the fitter and a range for every number in one representation

    Rejected Point probabilities with a separate "confidence" column; logistic regression (needs data we do not have yet)

  7. D7

    Review scheduler

    py-fsrs (open FSRS, MIT) with default weights, evidence mapped to ratings with weights; due = R(next drop) < 0.85; grammar structures capped at 3-day intervals for their first three reviews [DECISION, PRD-v2 9.4]

    Why The best-evidenced scheduler available, zero research cost; the caps implement "every 1 to 3 days early"

    Rejected Half-life regression (needs training data); a hand-made Leitner (worse by the published benchmarks)

  8. D8

    Structure evidence

    structure_observations rows (one per obligatory context) plus a structure_map summary; the 14-day accuracy is a query, never a stored counter [DECISION, PRD-v2 8.3, 10.6]

    Why Claims need evidence links to the exact turn; windows must be recomputable after a rebuild

    Rejected Counters in the map only (no evidence to open)

  9. D9

    Life facts

    life_facts with quote_event_id, a three-rung ladder (heard_once, usable, ground_truth), sensitivity class, valid_from/expires_at, supersession chain; sensitive candidates are never stored unconfirmed [DECISION, PRD-v2 8.4]

    Why The quote check is a database lookup, not a prompt; the editor's check 4 becomes a join

    Rejected Free-text memory summaries (the lens evidence: drift, overwrite, hallucination)

  10. D10

    Fact confirmation by viewing

    A fact_card_viewed event with dwell ≥ 4 s and no edit within the same notebook visit promotes heard_once to usable [DECISION, PRD-v2 8.4.2]

    Why The PRD rule needs a measurable "viewed"; 4 s is long enough to read a card

    Rejected Promotion on any render (the learner may never have looked)

  11. D11

    Show canon and callbacks

    show_canon rows written by the analyst; conversation_chunks with a pgvector column and exact (brute-force) search filtered by learner, no ANN index in the beta [DECISION, PRD-v2 14.3]

    Why A learner has under 2,000 chunks in year one; exact search is under 5 ms and always correct; the vector column exists only for callbacks, as the PRD limits it

    Rejected HNSW over all learners (filtered ANN recall problems, operational noise for nothing)

  12. D12

    Compiled briefs

    briefs.compile(role, learner_id, scope) with a briefs cache keyed by (learner_id, role, learner_model_version, scope_id); the stable part of every brief is ordered first for prompt caching [DECISION, PRD-v2 8.6]

    Why A new version invalidates by construction; no TTL logic

    Rejected Compile on every read (5 s teacher compile on every swap); a materialized view (cannot be role-shaped)

  13. D13

    Claims store

    claims table owned here, written only by the assessment domain's claim gate; shown_at is set by the surface that shows it; a rebuild never deletes a shown claim, it writes claim_invalidations for Salma's next proof [DECISION, PRD-v2 8.5, 10.10]

    Why The proof producer must read exactly one table; the "never retract silently" rule needs a record

    Rejected Claims recomputed on read (a shown claim would vanish after a rebuild)

  14. D14

    Rebuild

    learner/rebuild Inngest function: replay the learner's events into a shadow schema, run the after-pass writers at the new code versions, diff, swap in one transaction with a version bump of cause rebuild [DECISION, PRD-v2 8.5]

    Why Stores are disposable by design; the shadow schema makes a rebuild safe while the learner is using the app

    Rejected In-place rewrite (a learner mid-session reads half-rebuilt stores)

  15. D15

    Object storage keys

    {learner_id}/... prefix on every learner object in all three buckets; voice objects under .../ephemeral/... when storage is off so one lifecycle rule is the backstop [DECISION, PRD-v2 12.5, 12.6]

    Why Per-learner prefix makes export, deletion and lifecycle rules prefix operations; media_objects stays the index

    Rejected Content-addressed keys (deletion needs the index anyway, and prefix listing is the audit)

  16. D16

    Export

    Zip with manifest.json, learner_model.json (the nine stores), events.ndjson, transcripts/, notebook.json, audio/ (kept audio only), built by learner/export; presigned link valid 7 days, emailed within 1 h; the zip is encrypted with a one-time passphrase shown in the app, not in the email [DECISION, PRD-v2 12.5.7]

    Why Plain JSON as promised; the passphrase keeps an intercepted email from being the whole data set

    Rejected Unencrypted zip behind a presigned URL (one forwarded email leaks a voice archive)

  17. D17

    Deletion

    Access revoked synchronously; purge in a fixed table order inside 24 h; DEK destroyed last; deletion_ledger row with a salted hash of the email so a re-signup is not blocked but the 30-day backup expiry can be audited; RDS automated backup retention set to 30 days so "purged from backups within 30 days" is true by configuration [DECISION, PRD-v2 12.5.8]

    Why Matches the promise with no custom backup scrubbing

    Rejected Rewriting backups (not possible with RDS snapshots); 7-day retention (breaks PITR for an incident)

    Research set

    research_transcripts is populated only while data_use consent is on, from text only, under a pseudonymous id; revoking consent or deleting the account removes the learner's rows [DECISION, PRD-v2 12.5.5]

    Why "Never sold" and "theirs" read naturally as revocable

    Rejected Keeping anonymized rows after deletion (defensible legally, wrong for the trust contract) [OPEN for Muath, section 10]

Section 10. Only you can settle these; the document says what each answer changes.

  1. English Grammar Profile permission (PRD-v2 Part 18 #8), by 2026-11-09

    The structures table ships either way (D19), but the beta's inventory labels, bands and ids come from EGP if permission is granted; if not, the fallback is the kit's hand list plus public CEFR descriptors, which is thinner (about 150 structures instead of 300) and must be grown by hand during the beta. Money or a letter to Cambridge.

  2. Research rows after deletion

    D18 deletes a learner's anonymized transcripts when they delete the account or revoke data use. A less strict reading keeps already-anonymized rows. The trust contract reads better with deletion; the teacher improves slower. Confirm D18 or allow retention, and the consent copy changes with it.

  3. Processors that hold learner text

    Langfuse (traces with prompts and completions) and the embedding vendor (OpenAI by the topology's default) receive learner speech and chat text. Deletion depends on their deletion APIs. Approve both under PDPL, or fund self-hosting Langfuse (the topology's costed alternative) and a local embedding model (about one engineer-week).

  4. The name clip

    The learner's own recording of their name (A3) is voice data kept for name pronunciation regardless of voice-storage consent in the pipeline's assumption. Either the consent copy says so in one sentence ("we keep the 3-second clip of your name so the hosts say it right; delete it any time in Controls"), or the clip is deleted on revoke and the hosts use the respelled text only. Counsel and brand voice.

  5. The 30-day backup statement

    The privacy text must say "deleted from live systems within 24 hours and from backups within 30 days" and the RDS retention must be exactly 30 days (not longer for operational comfort). Confirm the wording with counsel so engineering sets the number once.

  6. Storage growth of kept voice (money)

    At 10,000 learners with 60% keeping recordings, voice storage grows about 3.6 TB a year (about $85/month at list), on top of the produced-audio archive the topology already flagged (open item 10 there). Both are small now; confirm they are acceptable or set a per-learner retention (for example, call audio older than two seasons is deleted unless marked kept) that the consent copy must then state.

  7. Export form

    D16 shows the zip passphrase in the app, not in the email. Learners who export and then delete the account before opening Controls lose the passphrase. Alternative: no passphrase and a 24-hour link. Pick one; both are one line of code.

  8. Who may run a rebuild in the beta

    A rebuild can invalidate shown claims, which Salma must then mention (PRD-v2 8.5). Decide whether rebuilds during the paid beta need your sign-off per cohort (the /admin button asks for a reason either way).

  1. blocker

    The rebuild design contradicts itself and the PRD.

    Where, evidence and fix

    3.3 flow D 'A rebuild' and 9.4 ('its stages are pure functions ... so learner/rebuild can re-run them without vendor calls')

    The rebuild design contradicts itself and the PRD. PRD 8.5 triggers a rebuild when the analyst, edit classifier or measures change version; the analyst and memory keeper are models (PRD 10.2 steps 2 and 7, 14.1), so a rebuild after an analyst change must re-call a model over every stored session. The document says 'no new vendor calls' while 9.4 says 'the analyst and classifier are re-run'. Worse, the model's proposals (AfterPassResult) are never appended to the log: the taxonomy has no event for analyst or memory-keeper output, so a code-only rebuild (classifier, measures, scheduler, updater) cannot replay without re-calling the model either. PRD 8.1 says the log is the source of truth and models only propose; the proposals are therefore part of the record.

    Evidence PRD 8.1, 8.5, 10.2, 14.1 ('Analyst: small model with a fixed schema'). Cost: analyst plus memory keeper is $0.04 per session (PRD 14.5); 100 learners x 20 sessions x 1 month = $80 per rebuild in December, about $8,000 per rebuild at 10,000 learners with a year of history; the stated '2 s per session' ignores model latency entirely.

    Fix Add an after_pass_result (+) event type that stores the validated AfterPassResult with analyst, classifier and memory_keeper versions. Define two rebuild kinds: (a) code-version rebuild replays stored results through the new code (no vendor calls, 2 s per session); (b) model-version rebuild re-calls the analyst and memory keeper, is costed per learner, runs in batch pricing, and needs the [OPEN for Muath] sign-off already proposed in section 10 #8. State both costs in section 6.

  2. major

    The database does not enforce (learner_id, event_id) uniqueness: on a table partitioned by occurred_at, the only unique constraint possible is the PK that includes occurred_at.

    Where, evidence and fix

    4.1.2 DDL and 4.1.3 Idempotency ('Uniqueness is (learner_id, event_id); the primary key includes occurred_at only because Postgres requires the partition key')

    The database does not enforce (learner_id, event_id) uniqueness: on a table partitioned by occurred_at, the only unique constraint possible is the PK that includes occurred_at. Combined with 4.1.4, which replaces occurred_at with recorded_at on skew, the same event can be inserted twice: first attempt arrives late and gets server time; the offline replay with the X-Forone-Replay header keeps the original timestamp; different partition key, no conflict, two rows. Play completions, taps and call turns then double-count, which breaks the active-day rule (PRD 3.6) and the hours count (PRD 12.3).

    Evidence PostgreSQL partitioned tables require unique indexes to include all partition key columns; 4.1.4's skew rule mutates the partition key; topology 4.2 requires unique (learner_id, client_event_id).

    Fix Never mutate occurred_at; store the server's corrected time in a separate effective_at column (or in payload) and order by (coalesce(effective_at, occurred_at), seq). Enforce uniqueness with a small unpartitioned event_ids (learner_id, event_id) primary key table written in the same statement (insert ... on conflict do nothing returning drives which rows go into events). Also align the column names with the topology contract (client_event_id, received_at) or note the rename in section 9.

  3. major

    retrievability returns 0.0 for any card in state New, and due_list selects every structure with state <> 'not_seen' and every word with status <> 'unseen', then sorts ascending by R and keeps the first 60.

    Where, evidence and fix

    4.5.3 due_list and retrievability

    retrievability returns 0.0 for any card in state New, and due_list selects every structure with state <> 'not_seen' and every word with status <> 'unseen', then sorts ascending by R and keeps the first 60. Every merely heard structure (fsrs state new, never reviewed) and every heard-only word with no review therefore sits at R = 0 at the top of the list and crowds out the genuinely due items; and kept words, which the text says 'enter the due list regardless of R', are sliced away by [:60] when their R is high. The teacher brief's due list (PRD 8.6 'the full due list', 9.4.2) is wrong on both counts.

    Evidence PRD 9.4.2 'Due means predicted recall below 0.85 by the next drop time'; PRD 9.5.4 'Kept words are scheduled like targets'; the code as written in 4.5.3.

1. Summary and the decisions in one table

1,534 words

The learner model is one append-only table of events and nine derived tables that any engineer can drop and rebuild from the events in under a minute per learner. Nothing a model says is written directly: the after-session pass hands this domain a fixed-schema result, code validates it (every life fact's quote must exist word for word in a verbatim transcript or chat message), applies it in one transaction, and bumps a per-learner integer learner_model_version. Every brief a role reads, every model call and every claim shown carries that integer, so a bad episode can be traced to exactly the model state that produced it. The scheduler is the open FSRS algorithm (py-fsrs) with a 0.85 recall threshold at the next drop time; word knowledge is a Beta distribution per word and surface, so every number has a range for free. Audio lives in S3 under per-learner keys at predictable paths; text lives in Postgres with row-level security; export is a zip built from the same tables; deletion is a row-ordered purge plus key destruction, with the 30-day backup window stated as a fact of RDS retention, not a promise we have to engineer.

3.3 The four flows

A. A session's events (write path, live). web buffers events for up to 2 s and posts batches of up to 50 to POST /v1/events with the session cookie; the server sets forone.learner_id for RLS, validates each payload against its type schema, drops duplicates on (learner_id, event_id), assigns seq from a per-connection bigserial, inserts in one statement, and returns {accepted, duplicates, rejected[]}. The same call computes whether the day just became active (PRD-v2 3.6) and, if so, sends day.became_active (topology). The worker posts through POST /internal/events with a service token; the payload is identical. No store is touched on this path.

B. The after-session pass (write path, within 10 min). The assessment domain's session/after-pass produces one AfterPassResult (4.3.0). Stage 1 (notes within 90 s) reads briefs and events only. At the end of stage 7 it calls stores.apply_after_pass(result), which in one transaction: validates every life-fact candidate against the log, applies word, structure, error, skill, interest, goal, taste and canon updates, runs the scheduler for every unit touched, bumps the version with cause after_pass, writes a learner_model_versions row with the high-water seq and the code versions (analyst, classifier, measures, memory_keeper, scheduler), and returns the new version. The caller then sends session.after_pass.completed {learner_id, session_id, learner_model_version} (topology event).

C. A learner edit (write path, synchronous). web posts a fact_card_edit, notebook_edit, working_on_edit, wrong_memory_flag or consent_change event. api appends it and, in the same transaction, calls stores.apply_learner_edit(event), which changes the one store row the edit names, bumps the version with cause learner_edit, and returns. For working_on_edit it then sends working_on.changed; for consent_change it sends learner.consent_changed. The response carries the new learnerModelVersion (the topology's cache key). This is the only store write outside workflows.

D. A rebuild. Triggered by learner.rebuild_requested {learner_id, reason} (new event, section 3.4) from /admin when a code version in code_versions changes, or in bulk by a script. learner/rebuild creates shadow copies of the nine tables for that learner (stores_shadow schema, same DDL), replays sessions in order by calling the assessment domain's pure functions over the stored verbatim turns and chat messages (no new vendor calls: transcripts are events), applies each result with the shadow writers, replays learner edits at their positions in the log, then swaps shadow rows for live rows in one transaction with cause rebuild. It compares the claims the new stores would support with the claims already shown; any shown claim no longer supported gets a claim_invalidations row (4.10). Duration: about 2 s per session of history on one worker; a learner with 100 sessions rebuilds in under 4 minutes.

4.1.3 Idempotency

  • event_id is a UUIDv7 minted by the producer at the moment the event happens (the PWA, the worker, or the workflow step). The time prefix makes it sortable and lets the server reject ids more than 7 days old or in the future.
  • Uniqueness is (learner_id, event_id); the primary key includes occurred_at only because Postgres requires the partition key in it. A duplicate is detected before insert with on conflict do nothing and reported in AppendResult.duplicates; it is never an error, because the offline queue and worker retries will send duplicates by design.
  • For events the workflow produces inside a retried step, the step derives event_id deterministically: uuid5(namespace, f"{run_id}:{step}:{key}"), so a retry appends nothing new.
  • Batches are atomic per request: either every non-duplicate row is inserted or none.

4.1.4 Ordering

  • occurred_at is the producer's clock. api compares it to its own clock at receipt: if the skew is over events.client_clock_skew_max_s (300 s) and the batch is not an offline replay (X-Forone-Replay: 1 header carrying the queue's original timestamps), occurred_at is replaced by recorded_at and the event is flagged payload._clock_corrected=true.
  • Within one learner, replay order is (occurred_at, seq). seq breaks ties and preserves arrival order for events with equal timestamps (the worker emits call_turn and silence at the same millisecond).
  • Cross-learner order does not matter anywhere.
  • The after-session pass is triggered by call.ended/chat.closed and reads whatever events have arrived by the time its stage runs; an event that arrives after the pass (an offline replay a day later) is folded in by the next pass or by a rebuild. That is why stores are rebuildable rather than exactly-once.

4.1.5 Retention

Events are kept for the life of the account (they are the learner's data and the only source of rebuilds). On deletion, the learner's rows are removed from every partition (4.12). Months older than 24 months may be moved to cheaper storage later; nothing in the beta does this. [ASSUMPTION] At 10,000 learners, about 300 events per session and 20 sessions a month, the table grows by about 60M rows (about 60 GB with payloads) a month; that is ordinary for RDS with monthly partitions and is addressed in section 6.

# forone/learner/versions.py
def bump(conn, learner_id, cause, *, session_id=None, stores_touched, code_versions) -> int:
    """Must run inside the caller's transaction. Serializes writers per learner with a row lock."""
    row = conn.execute(text("select lm_version from learners where id=:l for update"), {"l": learner_id}).one()
    new = row.lm_version + 1
    hw = conn.execute(text("select coalesce(max(seq),0) from events where learner_id=:l"), {"l": learner_id}).scalar()
    conn.execute(text("""insert into learner_model_versions(learner_id, version, cause, session_id, high_water_seq, code_versions, stores_touched)
                         values (:l,:v,:c,:s,:hw,:cv,:st)"""), dict(l=learner_id, v=new, c=cause, s=session_id, hw=hw,
                         cv=json.dumps(code_versions), st=stores_touched))
    conn.execute(text("update learners set lm_version=:v where id=:l"), {"v": new, "l": learner_id})
    append_event(conn, learner_id, type="lm_write", door="n/a", source="wf" if cause != "learner_edit" else "api",
                 payload={"learner_model_version": new, "cause": cause, "code_versions": code_versions, "high_water_seq": hw})
    return new

Where the version is recorded: briefs.learner_model_version; CallMeta.learner_model_version on every adapter call (topology 4.5), so vendor_calls and Langfuse carry it; events.learner_model_version on model-produced events; claims.learner_model_version; episodes.model_versions already exists, and the pipeline's EpisodePlan.learner_model_version is the string form lm_v_{n}. The string form is only for serialization; comparisons use the integer.

Every store table has learner_id, lm_version (the version of the write that last touched the row), updated_at, RLS as in 4.1.2, and an index starting with learner_id. Every estimate is stored as parameters from which a range follows (Beta for probabilities, mean and standard deviation for scales), never as a bare point.

4.5 Word probabilities and the review scheduler (code)

4.5.1 Priors

For an unseen unit, p0 = clip(sigmoid((size_est - rank) / (0.35 * size_est)), 0.02, 0.98) (the pipeline document states this shape; it is owned here). size_est comes from the word check: hits - false_alarms per band maps to a families estimate by the package's band table; no word check or fewer than 12 answers gives the B1 default prior.size_default = 3000 with size_sd = 1200. Chunks use the rank of their rarest content lemma plus 2,000. Stored as a Beta with concentration prior.k = 4: a = p0 * 4, b = (1 - p0) * 4, so two taps outweigh the prior and ten uneventful hearings are needed to move it far. The eye prior equals the ear prior plus 0.05 (reading is easier for this learner profile, PRD-v2 1.4); the produced prior is p0 * 0.6.

4.5.2 Evidence to Beta updates

Weight is applied as a fractional review: the FSRS update is computed for the rating and the new stability is S' = S + w * (S_fsrs - S). Ranges: p_low, p_high are the Beta 10% and 90% quantiles. Time: when last_seen_at is older than 30 days, p_understood returns mean * max(R(now), 0.6), so a word unused for months is treated as shaky again (the personalization lens's rule) without a separate decay model.

4.5.3 The scheduler

# forone/learner/scheduler.py
from fsrs import Scheduler, Card, Rating, State       # py-fsrs (MIT); weights = FSRS-4.5 defaults until we fit our own
_s = Scheduler(desired_retention=0.85)               # PRD-v2 9.4: due = predicted recall below 0.85

STRUCTURE_EARLY_CAP_DAYS = (1, 3)                    # grammar targets spaced tightly early (PRD-v2 9.4.3)

def review(card: Card, rating: Rating, weight: float, at: datetime, is_structure: bool) -> Card:
    new, _log = _s.review_card(card, rating, review_datetime=at)
    if weight < 1.0:                                 # fractional review for weak evidence
        new.stability = card.stability + weight * (new.stability - card.stability) if card.stability else new.stability
        new.due = at + timedelta(days=_s.next_interval(new.stability))
    if is_structure and new.reps <= 3:
        lo, hi = STRUCTURE_EARLY_CAP_DAYS
        new.due = at + timedelta(days=min(max((new.due - at).days, lo), hi))
    return new

def retrievability(card: Card, at: datetime) -> float:
    if card.state == State.New or not card.stability: return 0.0
    t = max((at - card.last_review).total_seconds() / 86400, 0)
    return (1 + t / (9 * card.stability)) ** -1       # FSRS forgetting curve

def due_list(conn, learner_id, at_drop: datetime) -> list[DueItem]:
    """Everything whose predicted recall at the next drop is below 0.85, plus kept words and active structure targets."""
    rows = conn.execute(text("""
      select 'word' as kind, unit_id as id, fsrs, kept, status from word_bank where learner_id=:l and status <> 'unseen'
      union all
      select 'structure', structure_id, fsrs, false, state from structure_map where learner_id=:l and state <> 'not_seen'"""), {"l": learner_id})
    out = []
    for r in rows:
        card = Card.from_dict(r.fsrs); R = retrievability(card, at_drop)
        if R < 0.85 or r.kept:
            out.append(DueItem(kind=r.kind, id=r.id, p_recall_at_drop=R, stability=card.stability, last_seen=card.last_review, kept=r.kept))
    return sorted(out, key=lambda d: d.p_recall_at_drop)[:60]   # the teacher never needs more than 60 candidates

The due list is computed at brief-compile time, not by a cron: it depends on the next drop time, which learner_schedule knows. def verify_quote(conn, learner_id, quote: str, quote_event_id: UUID) -> QuoteCheck:
    ev = conn.execute(text("select type, payload from events where learner_id=:l and event_id=:e"), {"l": learner_id, "e": quote_event_id}).one_or_none()

4.7.3 Sensitivity

A candidate with sensitivity set (the memory keeper proposes the class; code also forces the class from fact_shelf_life.sensitive_default) is stored only if confirmed_in_session = true; otherwise it is discarded and only the transcript keeps it. Stored sensitive facts get sensitive_usable_until = the Sunday ending the ISO week of said_at (Saudi weeks start Sunday; use the learner's local calendar) and are excluded from facts_usable after that date; they are never offered to the teacher as a callback or idea source (facts_usable returns them with may_initiate = false; the teacher's prompt rule "never brought up first" is enforced by filtering them out of facts_allowed unless the idea's topic came from the learner's own idea_chosen{source:'tell_salma'} in the same week). Nothing in this domain ever sets a sensitivity class from inference: the class comes only with a quote.

4.7.4 Time: shelf life, supersession, follow-ups

  • expires_at = valid_from + fact_shelf_life.shelf_days unless the type has null (dated plans expire the day after dated_event_on). Expired facts are status='dormant': kept, shown in the notebook under "earlier", never spoken.
  • Supersession: a new candidate with the same fact_type and a supersedes_hint or the same people.relation (new job, moved city) sets the old row status='superseded', superseded_by_fact_id=new and the new row supersedes_fact_id=old; facts_usable exposes history: [old.text] so the writer can say "how's the new job?".
  • Follow-ups: when a stored fact has dated_event_on, one follow_ups row is created with due_on = dated_event_on + 1 day; the teacher's follow_ups_due includes rows with state='pending' and due_on <= next drop date; the pipeline marks used with the episode id; expired after 21 days unused; cancelled if the fact is deleted.
