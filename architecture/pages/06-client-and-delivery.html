Client app, podcast feed and delivery

The installable web app, the private podcast feed and the three messages the product may send, with every rule kept on the server.

In one paragraph

The client is a thin, logic-free installable web app whose job is to play audio well, show text in two directions well, and send honest events. Every rule about the learner (doors, the allowance, consent, counts) lives in api; the client reflects it. The private podcast feed is a first-class second channel that carries the part of the product phone browsers do worst (lock-screen listening on the commute) and hands the learner back to the app for the call through one link. Three message kinds leave the product and the service worker refuses to render anything else.

The decisions

Section 1's table, one card per decision. "Rejected" is what was considered and turned down.

  1. D1

    Next.js 15 (App Router, React 19, TypeScript) on Vercel Pro, one project serving two hostnames: forone.app (public: landing, sample, share, invite, legal) and app.forone.app (the PWA). web holds no vendor key and no learner logic [DECISION, confirms topology D2; PRD-v2 1.4]

    Why Server rendering for the Arabic landing page, mature PWA tooling (Serwist), Git-integration deploys, one engineer can ship it; two hostnames keep the PWA's cookie jar, service-worker scope and edge caching clean

    Rejected Vite SPA (no SSR landing, no edge cache); Remix or SvelteKit (smaller hiring pool, no gain); Expo/React Native (PRD 1.4: native after the beta); HTMX from the Python API (a karaoke player and a WebRTC screen need a client framework)

  2. D2

    PWA through @serwist/next: precached shell; today's episode (app audio, timings.json, glosses.json, package.json, article and recap audio) plus the last two episodes stored in Cache Storage by an explicit page-side cache.add(); cached audio is played from a Blob URL read out of Cache Storage, never through the service worker's fetch handler; offline event queue in IndexedDB replayed for 24 h [DECISION; PRD-v2 1.4, 15]

    Why Dropped episode starts in under 2 s from local bytes; the bus has no signal; Safari's handling of media-element Range requests through a service worker has a history of bugs, and a Blob URL of a 6 MB file sidesteps it entirely while keeping seeking and Media Session; iOS evicts storage of non-installed sites after 7 days of disuse but exempts home-screen apps, which A10 asks for

    Rejected Streaming only (fails on the commute); relying on RangeRequestsPlugin for playback (kept only as a fallback for the uncached-but-partially-fetched case); caching every episode (quota and eviction on iOS)

  3. D3

    Player: one <audio> element on the stitched app file (episode.m4a) for every ready episode; a two-element scene handoff only while an on-demand episode is still streaming (swap, return, pilot, sample); Media Session for lock screen and headphones; speeds 0.75, 0.85, 1.0 and nothing above [DECISION; PRD-v2 5.1, 3.6, 3.8]

    Why One element keeps the lock-screen position, scrubbing and Media Session simple on iOS; a seam gap of 100 to 300 ms on the scene handoff is acceptable only where the script already has a sting or beat, which is exactly where the pipeline's segments end (segments[].seam)

    Rejected MSE/ManagedMediaSource (iOS support too new, no gain for a 6 MB file); per-segment elements everywhere (topology 4.6; gapless handoff is unreliable on iOS and complicates seeking)

  4. D4

    Word sheet is a local lookup in the shipped WordIndex; the word's audio is a play of the cached episode audio at [s, e] on a second, hidden audio element sharing the same Blob URL; phrase selection resolves to a chunk gloss if the span is a known chunk, else the stacked single-word glosses [DECISION; PRD-v2 5.7]

    Why 300 ms allows no network; the gloss cache is the pipeline's; the host's voice comes from the episode bytes already on the device

    Rejected Server lookup on tap; synthesizing the word

  5. D5

    Private feed: RSS 2.0 with the iTunes namespace at GET /f/{token}.xml; enclosures at GET /f/{token}/{episodeId}.mp3 served by api with Range passthrough (the topology's route); the enclosure is an MP3 (episode_feed.mp3, 96 kbps mono) rendered by the pipeline's mix step next to its AAC app file [DECISION; PRD-v2 3.3, 5.1, 12.6]

    Why The token in the path is the only credential podcast apps can carry; MP3 is the one format every podcast app plays and seeks; Range is what every app uses to resume; Part 18 #11 says the apps Saudi learners use are unknown, so the format with zero compatibility risk wins one extra ffmpeg encode

    Rejected AAC .m4a enclosure (the pipeline's episode_feed.m4a; Apple Podcasts and most Android apps play it, but moov-at-end files break seeking unless fast-started and a few Android apps still refuse audio/mp4; kept as the fallback if the pipeline cannot add the encode: then the enclosure is audio/mp4 with -movflags +faststart and the week-3 podcast-app test decides); signed expiring URLs (podcast apps cache the enclosure URL for days)

  6. D6

    Feed listening is never counted as a play event. Fetches are logged server-side in feed_fetches (user agent, range, bytes) for operations and Part 18 #11; hours heard credits a feed episode once at full length only when the learner later uses that episode's call, chat or small door (the data domain's rule, its 4.3.9); the return episode is triggered by an app open or a feed deep-link tap, never by a feed poll or an enclosure download [DECISION; PRD-v2 12.3, 3.8]

    Why Apple Podcasts and others auto-download new items, so an enclosure fetch is not a play; counting it would fake activity, which law 1 and the trust contract forbid

    Rejected Treating a full-file Range fetch as a play (PRD-v2 3.8.3 says "plays the feed"; topology 3.6 says "feed fetch"; see section 10 item 6)

  7. D7

    Feed-to-call handoff through a feed link token: the feed item's notes carry https://app.forone.app/call/{episodeId}?k={feedLinkToken}; api exchanges k for a limited session (scope feed_link: this episode's call, article, chat and Today; nothing in Controls, billing, export or deletion) in whatever browser opens it [DECISION; PRD-v2 5.1, 5.4.1, 16.2]

    Why On iOS the podcast app opens the link in Safari, which shares no cookies with the installed PWA; without a token the learner would have to sign in before every call from the feed, which is the handoff the beta is told to watch (19.3)

    Rejected Requiring sign-in (loses the handoff, the very metric 19.3 uses to decide on native); a full session from the link (a forwarded feed link would then open Controls)

  8. D8

    Web push with VAPID from api; one subscription row per browser context; the service worker renders only kind: drop and kind: gap_note payloads and drops anything else; title and length only [DECISION; PRD-v2 3.3, 3.10]

    Why Three message kinds is a hard rule; enforcing it in the sender and in the renderer means a bug in one cannot leak a fourth kind

    Rejected Firebase Cloud Messaging (another processor, no gain on the web); local notifications (not available to PWAs on iOS)

  9. D9

    Auth: email one-time code, Sign in with Apple, Google, implemented in api (Authlib plus our own OTP) with HttpOnly cookie sessions on .forone.app; onboarding runs on an anonymous pre_account session that the sign-in at A9 claims [DECISION, confirms topology D12; PRD-v2 1.4, 2.2 A9]

    Why Account only after the first call means the learner has state before an identity; claiming a pre-account row is a one-row update

    Rejected Clerk/Auth0 (PII in a US processor); passwords (PRD 1.4 chose codes)

  10. D10

    Install handoff on iOS through a per-learner start_url: the web manifest is served dynamically with start_url=/today?h={handoffToken} (single use, 7 days) so the home-screen app opens signed in [DECISION; PRD-v2 2.2 A10]

    Why Safari and a home-screen web app have separate cookie jars on iOS; without this the first thing the installed app shows is a sign-in screen, right after A10 asked for the install

    Rejected Asking the learner to sign in again (one email code; the single-engineer cut)

  11. D11

    API: REST JSON under /v1, OpenAPI generated by FastAPI, openapi-typescript plus openapi-fetch client; every response carries X-Forone-LM-Version (the topology's learnerModelVersion, one integer); events go in batches to POST /v1/events with client-minted UUIDv7 ids [DECISION, confirms topology 3.5; PRD-v2 8.2]

    Why Python backend rules out tRPC; GraphQL buys nothing for one client and thirteen screens; OpenAPI codegen gives typed calls for free

    Rejected GraphQL; tRPC; ad-hoc fetch

  12. D12

    Realtime: Server-Sent Events at GET /v1/stream for the foreground app (episode ready, notes ready, chat message, streaming manifest updates, voice-note replies), with ETag polling of GET /v1/today every 30 s as the fallback; nothing realtime is required for correctness [DECISION; PRD-v2 3.3, 5.5, 5.6]

    Why One-directional, works through the ALB with a 20 s heartbeat, native EventSource in every target browser, nothing to host

    Rejected WebSockets (bidirectional not needed outside the call, where LiveKit's data channel already exists); Pusher/Ably (another processor)

  13. D13

    State: TanStack Query for server documents, one Zustand store each for the player and the call, IndexedDB (idb) for the event queue and per-episode memory; the URL is the navigation state; no global store of learner facts [DECISION]

    Why Server documents are the truth; the two things with real local state (audio, call) get explicit state machines

    Rejected Redux; React context trees; a client-side copy of the learner model

  14. D14

    Bidi at the technical level: <html dir="rtl" lang="ar">, logical CSS properties only, dir="auto" plus unicode-bidi: plaintext on every content block, <bdi> for inline English inside Arabic, LTR for the transcript, article, captions and the scrub bar; Western digits; IBM Plex Sans Arabic with IBM Plex Sans as the Latin companion, self-hosted through next/font [DECISION; PRD-v2 1.4, 5.6, 12.1]

    Why Mixed-direction text is the single most common visual bug in Arabic apps; fixing it in one layout layer and one lint rule is cheaper than fixing it per screen

    Rejected Per-screen direction handling; Google Fonts at runtime (a third-party request per page)

  15. D15

    Analytics is the event log. No third-party analytics SDK, no fingerprinting, no session replay; Sentry for errors with PII scrubbing; four client-only event types (app_open, pwa_install, client_perf, push_permission) added to the log so 16.2's "unprompted return" and the latency budgets are measurable [DECISION; PRD-v2 16.2, trust promise 6]

    Why The product's own log already records everything pedagogically meaningful; any third-party SDK would be a processor under PDPL with no benefit

    Rejected GA4, Mixpanel, PostHog

  16. D16

    Sample page: text or voice answers, POST /v1/sample returns 202 {sample_id}, the page polls GET /v1/sample/{id} each second and plays from scene 1; a share page at forone.app/s/{sampleId} with Open Graph tags for WhatsApp; limits by first-party device cookie and contact hash in api [DECISION; PRD-v2 2.1]

    Why The 30 s budget is the pipeline's; the page only has to start on the first scene; sharing is the learner's choice through the native share sheet

    Rejected Auto-sharing; email capture before play

  1. The brand domain, by 2026-11-02

    forone.app is a placeholder in every document. Cookies, VAPID subject, the Apple Services ID, Google OAuth verification, the Apple relay email registration and the feed URLs all bind to it in week 1; changing it later costs a day and re-subscribing every learner's feed.

  2. Apple Developer Program ($99 a year) and Google Cloud OAuth verification, started by 2026-11-09

    Both take days to approve, and Apple's "Sign in with Apple for Email Communication" registration for the sending domain is part of the same setup (without it, codes and receipts to Apple-relay addresses bounce). If either slips, 2026-12-07 ships with the email code only and the two buttons appear in the beta (P1). The founding cohort is invited by hand, so the cost is one extra step at A9, not lost learners.

  3. Which three podcast apps A10 names

    This design prepares instructions for Apple Podcasts, Pocket Casts and Podcast Addict (Android). Spotify and YouTube Music do not accept private feeds and are named as "not supported" on the card. Confirm the three, or name the apps the Milestone 0 day-14 survey shows your learners use; the week-3 test on those three decides feed.enclosure_format.

  4. The feed-link session (D7)

    A forwarded feed link lets its holder start that episode's call and read the chat as the learner, until the link is reset in Controls. The alternative is sign-in before every call from the feed, which weakens the handoff 19.3 watches. Accept the limited session, or require sign-in.

  5. Digits and type

    Western digits (0 to 9) and IBM Plex Sans Arabic with IBM Plex Sans are this document's defaults. Both are brand calls; changing the font is a day, changing the digits is an hour, both before week 2.

  6. "Plays the feed" (PRD-v2 3.8.3)

    This design does not treat a feed download as a play (D6), so a learner who only listens through the podcast app sees the return episode when they next open the app or tap a feed link, not when the podcast app fetches. Confirm the deviation or ask for the fragile version (a Range fetch past 50% of the file by a non-auto-downloading app counts), which this document advises against.

  7. The public sample share page

    The share page plays the sample (which says the person's first name) to anyone with the link for 30 days, with a WhatsApp preview. It is what "the sample is theirs to keep and forward" needs; confirm with counsel that a first name in a public audio file is fine, or make the page require the sender's device cookie (which kills forwarding).

  8. Vercel and Resend as processors under PDPL

    Vercel serves the shell and keeps request logs (IP addresses) outside the GCC; Resend holds email addresses. Approve, or name replacements (Cloudflare Pages or static hosting on S3 and CloudFront in me-central-1 for the shell, about three engineer-days; Amazon SES for email, one day).

  9. The day-7 payment card on Today

    PRD-v2 0.1 row 8 says payment is asked once, plainly, on day 7. This design shows Salma's sentence and the plans as a card above the hero on day 7 until answered, and never blocks the episode. Confirm the placement, and what happens on day 8 to 90 (this design: the card stays, quietly, under the hero).

  10. One engineer or two

    Section 7 lists seven cuts in order. If the team is one engineer on 2026-11-02, cuts 1 to 3 are taken on that day.

  11. Device test budget

    About $40 a month for BrowserStack and two physical test phones (one iPhone on iOS 18, one Android on 14) for weeks 2 to 5. Approve or the suite becomes the manual checklist (cut 7).

  1. major

    The under-2-second dropped-episode path is premised on a cache warm that the design can only perform while the page is in the foreground, but tomorrow's episode is normally produced overnight in batch after the pick, so on most mornings the episode became ready while the app was closed and the warm never ran.

    Where, evidence and fix

    3.4 Data flows, flow A ("finds episode.m4a already in forone-media-v1 from the previous evening's today.changed") and 4.6 rule 1 ("the page (not the SW) runs cache.add()")

    The under-2-second dropped-episode path is premised on a cache warm that the design can only perform while the page is in the foreground, but tomorrow's episode is normally produced overnight in batch after the pick, so on most mornings the episode became ready while the app was closed and the warm never ran. The common path is therefore the cold network stream the document files under failure modes, and the budget is sized on the exception.

4.4 The player

4.4.1 Inputs. EpisodeDoc (title, cast, kind, state, player_defaults: {transcript_open: boolean, speed: 0.75|0.85|1.0, speech_rate}, media: {app, scenes[], article, recap, timings, glosses, package} as asset names, targets and new_words lemma lists for Huh? glossing, ask_followed), the pipeline's AudioManifest (timings.json: lines[] with sentences[] and words[], segments[] with seam and stream_url, pause_no_capture, timing_quality: "word"|"sentence", article_words[], shadow_lines[]) and WordIndex (glosses.json). On load the client builds two flat, sorted arrays: words: {s, e, line_id, i}[] and sentences: {s, e, sent_id, line_id, text}[], and a Map<line_id, Map<i, gloss_ref>> from the index. For a 900-word script this is under 5 ms.

4.4.2 State machine (PlayerStore, Zustand, one instance app-wide so Today, Show and the lock screen share it):

states: idle → loading → ready → playing ⇄ paused → ended → thrown

                                   any --(switch episode)--> loading
context: { episode_id, source: "blob"|"network"|"scenes", scene_index, position_ms, speed, transcript_open,

Transitions that matter for the laws: ended fires the completion event (play with position_ms = duration) and moves to thrown when the manifest's last line is the throw; in thrown the three choices (Call now, Read the article first, Later) are shown and the Media Session play action is a no-op (PRD 4 rule 2: pressing play on the headphones after the throw does nothing). There is no next state and no queue. "Later" simply closes the sheet; the Today doors show Call as not_started.

4.4.3 Audio elements. Three HTMLAudioElements created once per app load and unlocked on the first user gesture (play then pause on a 100 ms silent data URI; iOS allows programmatic play() later only on elements that have been started by a gesture): main (the episode or article or recap), clip (word sheet, notes clips, marked moments, shadow lines) and aux (the second element of the scene handoff while streaming). preservesPitch = true. playsinline. crossOrigin = "use-credentials" when the source is a network URL.

4.4.4 Source selection. (1) If forone-media-v1 holds the full episode.m4a for this manifest version: main.src = URL.createObjectURL(await (await cache.match(url)).blob()) (source: "blob"; the Blob URL is kept for the episode's lifetime and revoked on switch episode; clip shares it). (2) Else if manifest.timing_quality == "word" and the app file exists on the server: main.src = the network URL (source: "network"), with api's Range support for seeking, and the page starts cache.add() of the full file in the background so the next open is case 1. (3) Else (streaming): main.src = scene-{s0}, aux.src = scene-{s1} preloaded; on main.ended swap roles at the seam (the pipeline guarantees a sting or beat at every segment end); when episode.manifest arrives on the stream with the full file, the player switches to it at the next seam, seeking to the same absolute position (segment.start_ms + position). While streaming, sentences[] come from the manifest's sentence-level estimate and the transcript is folded regardless of the learner's default (pipeline 4.13 item 3).

4.4.5 Sync loop. requestAnimationFrame while playing (and a 250 ms setInterval when the tab is hidden, which iOS throttles but does not stop for playing audio): t = main.currentTime * 1000 + scene_offset; binary search words for the active word; if it changed, move the data-active attribute (one DOM write) and, when the active line changes, scroll the transcript so the current line sits at 40% of the viewport (scrollIntoView({block: "center"}) only when the learner has not scrolled in the last 3 s). Word spans are rendered once; nothing re-renders per frame.

4.5 The word sheet

Tap on a word span → index.script.get(line_id).get(i) → gloss_ref → index.glosses[gloss_ref] → render {meaning_ar, pos, register_note_ar, example_en} plus the sentence the word came from (sentences[] by sent_id) → measure word_sheet_open_ms from pointerup to first paint (PerformanceObserver on the sheet's element-timing), logged in client_perf when it exceeds 300 ms. 🔊 → clip.src = main.src (the same Blob URL or network URL), clip.currentTime = (w.s - 60) / 1000, play, pause at w.e + 60 ms (a timeupdate guard plus a setTimeout at the expected duration). Keep → keep {unit_id, sense_key, sentence_text} and an optimistic tick. The sheet is a bottom sheet that does not pause the main audio unless 🔊 is tapped (then main pauses for the clip and resumes).

Phrase selection: pointerdown on a word, pointermove across spans (with touch-action: pan-y so vertical scroll still works), pointerup → the span [i, j] within one line; if any index entry in the span carries a chunk_id whose extent equals [i, j], show the chunk's gloss (index.glosses[chunk gloss_ref]); otherwise show the per-word glosses stacked in order and log one tap per word with chunk: false. A 350 ms long-press on a single word selects it for the drag (iOS otherwise opens the text-selection UI; the transcript has user-select: none).

Misses: when index.missing[] contains the lemma, the sheet shows the sentence at once and calls GET /v1/gloss?lemma=&sense_key= (the pipeline's gloss-service.lookup) with a 1.5 s timeout and a plain "no meaning yet" fallback; this is the only network path on tap and it is rare.

4.6 Service worker and caching

Serwist configuration (sw.ts):

const sw = new Serwist({
  precacheEntries: self.__SW_MANIFEST,              // the Next.js shell: html, js, css, fonts, icons, Salma's static Arabic clips used by onboarding UI
  skipWaiting: true, clientsClaim: true, navigationPreload: true,

    { matcher: ({url}) => url.pathname === "/v1/today" || url.pathname.startsWith("/v1/shelf"),

  fallbacks: { entries: [{ url: "/offline", matcher: ({request}) => request.mode === "navigate" }] },

Rules the page enforces on top:

  1. Warm today's episode when TodayDoc.hero.state == "ready" or on today.changed {reason: episode_ready}: the page (not the SW) runs cache.add() for episode.m4a (a full 200 fetch), timings.json, glosses.json, package.json, article.m4a, recap.m4a into forone-media-v1; on a metered connection (navigator.connection.saveData) only timings.json, glosses.json and package.json are warmed and the audio streams from the network. web.sw.warm_assets is the list; web.sw.cache_episodes_n = 3 keeps today's and the last two; older entries are evicted by the plugin and the archive streams them on demand. Playback reads the cached entries through caches.match() and Blob URLs (4.4.4), so playback never depends on the SW's fetch handler being invoked for a media element, which Safari has historically done inconsistently.
  2. Never cache a partial response. A 206 from api is passed through and not stored (the plugin would otherwise store a truncated body).
  3. Quota. navigator.storage.estimate() on app start; under 100 MB free, cache_episodes_n drops to 1; persist() is requested once after install (granted automatically to installed PWAs on Chrome; iOS ignores it but exempts home-screen apps from the 7-day eviction).
  4. Versioning. Cache names carry a version; a new SW deletes caches with other versions on activate. Media keys are immutable per (episode_id, manifest_version) so a cached episode survives SW upgrades within a version; a republished manifest (streaming → word timings) changes the key and the page re-adds.
  5. Push and notification click (4.8) live in the same SW.
  6. Background Sync (forone-events) on Chrome replays the event queue when the page is closed; Safari has no Background Sync, so the queue is replayed on the next open (the 24 h window matches the data domain's clock-skew rule for replays).

The event queue (lib/events/queue.ts): IndexedDB database forone-queue, store batches keyed by batch_id, each a JSON array of EventIn. enqueue(event) buffers in memory for 2 s or 50 events, writes the batch, and posts it; on success the batch is deleted; on network failure it stays; on 4xx other than 429 the batch is marked rejected and reported to Sentry without payload text. Replays send X-Forone-Replay: 1. Batches older than events.queue_ttl_h = 24 are dropped and counted. occurred_at is the device clock at the moment of the event; the server corrects skew.

EpisodeMemory (IndexedDB forone-memory, store episodes keyed by episode_id): {position_ms, speed, transcript_opened_before, article_depth, last_opened_at}; written on pause, seek and every 5 s while playing; mirrored to the server through POST /v1/sessions/{id}/doors/{door} on pause and visibilitychange so the position survives a reinstall (PRD 4 rule 4).

PUT /me {birth_date} follows; under 18 deletes the pre-account learner and shows the plain message (PRD 1.4).
  3. Email code. POST /auth/otp/request always returns 202; rate limits: 3 per email per 10 min, 10 per IP hash per hour; the email is kind signin_code with the 6-digit code and nothing else; verify allows 5 attempts per code; the code is consumed on success.
  4. Apple. Services ID for app.forone.app, response_mode=form_post to /v1/auth/apple/callback, the state cookie carries the pre-account session id; Apple's private relay address is stored as accounts.email. Two practical requirements the week-3 checklist carries: the Apple Developer Program membership (section 10), and registering forone.app and show@forone.app under "Sign in with Apple for Email Communication" with SPF and DKIM on the sending domain, because mail to @privaterelay.appleid.com from an unregistered sender bounces, which would silently break sign-in codes, receipts and the export link for every Apple-relay learner.
  5. Google. OIDC authorization code with PKCE, prompt=select_account; the Google Cloud OAuth consent screen must be verified for forone.app (section 10).
  6. Sessions. Full sessions last auth.session_days = 90, rolling on use; signout revokes the row; account deletion revokes every row at once (data domain 4.12.2 step 1); api sets forone.learner_id for RLS from the row on every request.
  7. Install handoff (D10). The manifest route is a Next.js route handler on app.forone.app: it reads forone_s (same-origin, so the browser sends it with the manifest fetch), forwards it to POST /v1/handoff/mint (one token per learner per 7 days), and returns the manifest JSON with start_url: "/today?h=<token>", scope: "/", display: "standalone", id: "/", icons, theme_color from the show colour. A used or expired token simply shows the sign-in screen (no email prefilled, no leak). Android Chrome shares the jar, so the token is unused there and expires.
  8. Feed link sessions as in 4.7.
