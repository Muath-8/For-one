Client app, podcast feed and delivery

The installable web app, the private podcast feed and the three messages the product may send, with every rule kept on the server.

One review, revised 2026-11-06 19 decisions 15 open for Muath 25,659 words, about 110 min

One review, revised 2026-11-06. Only the conformance review ran; no skeptic review exists for this document. Its findings and the decision records were applied on 2026-11-06, so the text is current, but it has had one fewer pair of eyes than the others.

In one paragraph

The client is a thin, logic-free installable web app whose job is to play audio well, show text in two directions well, and send honest events. Every rule about the learner (doors, the allowance by plan, consent, counts) lives in api; the client reflects it. The interface speaks the learner's native language (strings, direction and fonts from packages/native/<lang>/, ADR-02); the content is in the target language. The screen shows the producer (Salma), the series and the weekly proof, never a correction list: there are no notes, no margin notes and no polish card (ADR-06), and "explain when asked" is a chat affordance to Salma. The private podcast feed is a first-class second channel that carries the part of the product phone browsers do worst (lock-screen listening on the commute) and hands the learner back to the app for the call through one link. Three message kinds leave the product and the service worker refuses to render anything else.

The decisions

Section 1's table, one card per decision. "Rejected" is what was considered and turned down.

  1. D1

    Next.js 15 (App Router, React 19, TypeScript) on Vercel Pro, one project serving two hostnames: forone.app (public: landing, sample, share, invite, legal) and app.forone.app (the PWA). web holds no vendor key and no learner logic; the Vercel region follows HOME_REGION (fra1 for eu-central-1, dxb1 if me-central-1 is chosen; ADR-08) [DECISION, confirms topology D2; PRD-v2 1.4]

    Why Server rendering for the landing page in the visitor's language (per Accept-Language, English default), mature PWA tooling (Serwist), Git-integration deploys, one engineer can ship it; two hostnames keep the PWA's cookie jar, service-worker scope and edge caching clean

    Rejected Vite SPA (no SSR landing, no edge cache); Remix or SvelteKit (smaller hiring pool, no gain); Expo/React Native for the beta (decisions.md §7's recommendation is web plus the feed; the question stays [OPEN for Muath], 10-decision-records §10 item 8, and section 8 says what a native pick changes); HTMX from the Python API (a karaoke player and a WebRTC screen need a client framework)

  2. D2

    PWA through @serwist/next: precached shell; today's episode (app audio, timings.json, glosses.json, package.json, article and recap audio) plus the last two episodes stored in Cache Storage, warmed by the service worker's push handler when the drop payload arrives (the app is normally closed when the episode becomes ready) and by the page while it is open; cached audio is played from a Blob URL read out of Cache Storage, never through the service worker's fetch handler; the cold network path is the sized path (section 6) because the warm cannot be guaranteed; offline event queue in IndexedDB replayed for 24 h [DECISION; PRD-v2 1.4, 15]

    Why Dropped episode starts in under 2 s from local bytes when warmed and inside the budget from the network when not; the bus has no signal; Safari's handling of media-element Range requests through a service worker has a history of bugs, and a Blob URL of a 6 MB file sidesteps it entirely while keeping seeking and Media Session; iOS evicts storage of non-installed sites after 7 days of disuse but exempts home-screen apps, which A10 asks for

    Rejected Streaming only (fails on the commute); relying on RangeRequestsPlugin for playback (kept only as a fallback for the uncached-but-partially-fetched case); caching every episode (quota and eviction on iOS)

  3. D3

    Player: one <audio> element on the stitched app file (episode.m4a) for every ready episode; a two-element scene handoff only while an on-demand episode is still streaming (swap, return, pilot, sample); Media Session for lock screen and headphones; speeds 0.75, 0.85, 1.0 and nothing above [DECISION; PRD-v2 5.1, 3.6, 3.8]

    Why One element keeps the lock-screen position, scrubbing and Media Session simple on iOS; a seam gap of 100 to 300 ms on the scene handoff is acceptable only where the script already has a sting or beat, which is exactly where the pipeline's segments end (segments[].seam)

    Rejected MSE/ManagedMediaSource (iOS support too new, no gain for a 6 MB file); per-segment elements everywhere (topology 4.6; gapless handoff is unreliable on iOS and complicates seeking)

  4. D4

    Word sheet is a local lookup in the shipped WordIndex; the word's audio is a play of the cached episode audio at [s, e] on a second, hidden audio element sharing the same Blob URL; phrase selection resolves to a chunk gloss if the span is a known chunk, else the stacked single-word glosses [DECISION; PRD-v2 5.7]

    Why 300 ms allows no network; the gloss cache is the pipeline's; the host's voice comes from the episode bytes already on the device

    Rejected Server lookup on tap; synthesizing the word

  5. D5

    Private feed: RSS 2.0 with the iTunes namespace at GET /f/{token}.xml; enclosures at GET /f/{token}/{episodeId}.mp3 served by api with Range passthrough (the topology's route); the enclosure is an MP3 (episode_feed.mp3, 96 kbps mono) rendered by the pipeline's mix step next to its AAC app file [DECISION; PRD-v2 3.3, 5.1, 12.6]

    Why The token in the path is the only credential podcast apps can carry; MP3 is the one format every podcast app plays and seeks; Range is what every app uses to resume; Part 18 #11 says the podcast apps learners use are unknown (and with no launch country they vary by market), so the format with zero compatibility risk wins one extra ffmpeg encode

    Rejected AAC .m4a enclosure (the pipeline's episode_feed.m4a; Apple Podcasts and most Android apps play it, but moov-at-end files break seeking unless fast-started and a few Android apps still refuse audio/mp4; kept as the fallback if the pipeline cannot add the encode: then the enclosure is audio/mp4 with -movflags +faststart and the week-3 podcast-app test decides); signed expiring URLs (podcast apps cache the enclosure URL for days)

  6. D6

    Feed listening is never counted as a play event. Fetches are logged server-side in feed_fetches (user agent, range, bytes) for operations and Part 18 #11; hours heard credits a feed episode once at full length only when the learner later uses that episode's call, chat or small door (the data domain's rule, its 4.3.9); the return episode is triggered by an app open or a feed deep-link tap, never by a feed poll or an enclosure download [DECISION; PRD-v2 12.3, 3.8]

    Why Apple Podcasts and others auto-download new items, so an enclosure fetch is not a play; counting it would fake activity, which law 1 and the trust contract forbid

    Rejected Treating a full-file Range fetch as a play (PRD-v2 3.8.3 says "plays the feed"; topology 3.6 says "feed fetch"; see section 10 item 6)

  7. D7

    Feed-to-call handoff through a feed link token: the feed item's notes carry https://app.forone.app/call/{episodeId}?k={feedLinkToken}; api exchanges k for a limited session (scope feed_link: this episode's call, article, chat and Today; nothing in Controls, billing, export or deletion) in whatever browser opens it [DECISION; PRD-v2 5.1, 5.4.1, 16.2]

    Why On iOS the podcast app opens the link in Safari, which shares no cookies with the installed PWA; without a token the learner would have to sign in before every call from the feed, which is the handoff the beta is told to watch (19.3)

    Rejected Requiring sign-in (loses the handoff, the very metric 19.3 uses to decide on native); a full session from the link (a forwarded feed link would then open Controls)

  8. D8

    Web push with VAPID from api; one subscription row per browser context; the service worker renders only kind: drop and kind: gap_note payloads and drops anything else; title and length only [DECISION; PRD-v2 3.3, 3.10]

    Why Three message kinds is a hard rule; enforcing it in the sender and in the renderer means a bug in one cannot leak a fourth kind

    Rejected Firebase Cloud Messaging (another processor, no gain on the web); local notifications (not available to PWAs on iOS)

  9. D9

    Auth: email one-time code, Sign in with Apple, Google, implemented in api (Authlib plus our own OTP) with HttpOnly cookie sessions on .forone.app; onboarding runs on an anonymous pre_account session that the sign-in at A9 claims [DECISION, confirms topology D12; PRD-v2 1.4, 2.2 A9]

    Why Account only after the first call means the learner has state before an identity; claiming a pre-account row is a one-row update

    Rejected Clerk/Auth0 (PII in a US processor); passwords (PRD 1.4 chose codes)

  10. D10

    Install handoff on iOS through a per-learner start_url: the web manifest is served dynamically with start_url=/today?h={handoffToken} (single use, 7 days) so the home-screen app opens signed in [DECISION; PRD-v2 2.2 A10]

    Why Safari and a home-screen web app have separate cookie jars on iOS; without this the first thing the installed app shows is a sign-in screen, right after A10 asked for the install

    Rejected Asking the learner to sign in again (one email code; the single-engineer cut)

  11. D11

    API: REST JSON under /v1, OpenAPI generated by FastAPI, openapi-typescript plus openapi-fetch client; every response carries X-Forone-LM-Version (the topology's learnerModelVersion, one integer); events go in batches to POST /v1/events with client-minted UUIDv7 ids [DECISION, confirms topology 3.5; PRD-v2 8.2]

    Why Python backend rules out tRPC; GraphQL buys nothing for one client and thirteen screens; OpenAPI codegen gives typed calls for free

    Rejected GraphQL; tRPC; ad-hoc fetch

  12. D12

    Realtime: Server-Sent Events at GET /v1/stream for the foreground app (episode ready, chat message from a host or Salma, streaming manifest updates, voice-note replies, Salma-made settings changes), with ETag polling of GET /v1/today every 30 s as the fallback; nothing realtime is required for correctness [DECISION; PRD-v2 3.3, 5.5, 5.6]

    Why One-directional, works through the ALB with a 20 s heartbeat, native EventSource in every target browser, nothing to host

    Rejected WebSockets (bidirectional not needed outside the call, where LiveKit's data channel already exists); Pusher/Ably (another processor)

  13. D13

    State: TanStack Query for server documents, one Zustand store each for the player and the call, IndexedDB (idb) for the event queue and per-episode memory; the URL is the navigation state; no global store of learner facts [DECISION]

    Why Server documents are the truth; the two things with real local state (audio, call) get explicit state machines

    Rejected Redux; React context trees; a client-side copy of the learner model

  14. D14

    Bidi at the technical level, language from the package: <html lang dir> set from GET /v1/package/ui (the native-language package's lang, dir, strings and font; RTL only when the learner's native language is RTL), logical CSS properties only, dir="auto" plus unicode-bidi: plaintext on every content block, <bdi> for inline target-language runs inside native text, the target language's direction for the transcript, article, captions and the scrub bar; Western digits by default (a package may override); the native package names its UI font (native/ar: IBM Plex Sans Arabic; native/en: IBM Plex Sans), with IBM Plex Sans as the Latin companion, self-hosted through next/font [DECISION; ADR-02; PRD-v2 1.4, 5.6, 12.1, 13.1, 13.2]

    Why Mixed-direction text is the single most common visual bug in RTL apps; fixing it in one layout layer and one lint rule is cheaper than fixing it per screen; one pair ships in the beta but the mechanism is honest (PRD 13.2)

    Rejected Per-screen direction handling; hard-coded lang="ar" and _ar field names (the first draft); Google Fonts at runtime (a third-party request per page)

  15. D15

    Analytics is the event log. No third-party analytics SDK, no fingerprinting, no session replay; Sentry for errors with PII scrubbing; four client-only event types (app_open, pwa_install, client_perf, push_permission) added to the log so 16.2's "unprompted return" and the latency budgets are measurable [DECISION; PRD-v2 16.2, trust promise 6]

    Why The product's own log already records everything pedagogically meaningful; any third-party SDK would be a processor under every regime in 07 §4.9 (GDPR, PDPL, the generic baseline) with no benefit

    Rejected GA4, Mixpanel, PostHog

  16. D16

    Sample page: text or voice answers, POST /v1/sample returns 202 {sample_id}, the page polls GET /v1/sample/{id} each second and plays from scene 1; a share page at forone.app/s/{shareToken} (the topology's unguessable share_token, never the poll handle) with Open Graph tags for WhatsApp; limits by first-party device cookie and contact hash in api [DECISION; PRD-v2 2.1; topology 9.5]

    Why The 30 s budget is the pipeline's; the page only has to start on the first scene; sharing is the learner's choice through the native share sheet; forwarding the share URL must not leak the poll endpoint

    Rejected Auto-sharing; email capture before play; sampleId in the share URL (the first draft)

  17. D17

    Salma has a thread. /chat/salma is a third thread on the same ChatDoc shape as the two hosts (text and hold-to-talk through the typed Salma turn the topology runs in api), reached from the Notebook header, every "Tell Salma" affordance ("Not quite right?" under Why this episode, a fact card's ✕, "where do I stand") and Controls; Salma's questions to the learner (the rhythm, the season goal, the gap note) are typed salma_ask messages inside a thread with a typed answer; Salma explains when asked and never corrects [DECISION; decisions.md §3; ADR-06; PRD-v2 12.4, 7.3.2, 10.8.3, 12.3, 3.9.4]

    Why The product routes settings by conversation, "what do you know about me?", "why do we say it like that?" and life updates through a sentence to Salma; without a surface those are dead ends; it is the same component as the host chat

    Rejected A settings form for each (PRD 12.4: "everything else is a sentence to Salma"); Salma's after-call notes (removed, ADR-06)

  18. D18

    Plans and checkout. Three USD monthly plans from plans.yaml (one_a_day $19.99, two_a_day $29.99 recommended and the trial plan, three_a_day $44.99); the plan picker is one sheet (/controls/plans, also the body of the day-7 card) laid out as decisions.md §2 asks: the middle plan marked "Recommended" and preselected, the top plan as the anchor, "about $1 a day", the tutor comparison, the founding price lock in one line, cancel in one tap; never a countdown, scarcity, guilt or a pre-ticked upgrade; checkout is the processor's hosted page through POST /v1/billing/checkout {plan} and the client never renders a card form, so Paddle (merchant of record, recommended) or Stripe with Stripe Tax fit without a client change [DECISION; ADR-04, ADR-21; processor [OPEN for Muath], 10-decision-records §10 item 3]

    Why Muath decided the tiers and asked for honest pricing psychology; a merchant of record handles tax in every country, which no launch country makes necessary

    Rejected SAR prices, a founding year, a yearly plan, Mada-first (PRD-v2 1.4); a card form in the client

  19. D19

    "Next one" is a Today control, not a player control. When the day's episode has ended (the throw answered or "Later") and TodayDoc.allowance.remaining_today > 0, Today shows one button "Next one" that calls POST /v1/episodes/next → 202 {episode_id}; the extra streams like a swap (episode_kind: daily_extra); the player has no next state, no queue and no autoplay; the Show tab lists all of the day's episodes [DECISION; ADR-05; concept-v2 law 11]

    Why Episodes 2 and 3 are made on request; the request must be a learner action with a clear ending before it

    Rejected Autoplay or a "next episode" queue in the player (law 11); pre-producing the allowance

7 blocker and major findings
  1. major

    The under-2-second dropped-episode path is premised on a cache warm that the design can only perform while the page is in the foreground, but tomorrow's episode is normally produced overnight in batch after the pick, so on most mornings the episode became ready while the app was closed and the warm never ran.

4.4 The player

4.4.1 Inputs. EpisodeDoc (title, cast, kind, state, player_defaults: {transcript_open: boolean, speed: 0.75|0.85|1.0, speech_rate}, media: {app, scenes[], article, recap, timings, glosses, package} as asset names, targets and new_words lemma lists for Huh? glossing, ask_followed), the pipeline's AudioManifest (timings.json: lines[] with sentences[] and words[], segments[] with seam and stream_url, pause_no_capture, timing_quality: "word"|"sentence", article_words[], shadow_lines[]) and WordIndex (glosses.json). On load the client builds two flat, sorted arrays: words: {s, e, line_id, i}[] and sentences: {s, e, sent_id, line_id, text}[], and a Map<line_id, Map<i, gloss_ref>> from the index. For a 900-word script this is under 5 ms.

4.4.2 State machine (PlayerStore, Zustand, one instance app-wide so Today, Show and the lock screen share it):

states: idle → loading → ready → playing ⇄ paused → ended → thrown

Transitions that matter for the laws: ended fires the completion event (play with position_ms = duration) and moves to thrown when the manifest's last line is the throw; in thrown the three choices (Call now, Read the article first, Later) are shown and the Media Session play action is a no-op (PRD 4 rule 2: pressing play on the headphones after the throw does nothing). There is no next state and no queue; the "Next one" request of ADR-05 lives on Today (D19), appears only once the player has left playing for thrown or ended and the throw's choice is made, and is never reachable from the player, the lock screen or the feed. "Later" simply closes the sheet; the Today doors show Call as not_started.

4.4.3 Audio elements. Three HTMLAudioElements created once per app load and unlocked on the first user gesture (play then pause on a 100 ms silent data URI; iOS allows programmatic play() later only on elements that have been started by a gesture): main (the episode or article or recap), clip (word sheet, marked moments, proof evidence, shadow lines) and aux (the second element of the scene handoff while streaming). preservesPitch = true. playsinline. crossOrigin = "anonymous" when the source is a presigned URL (ADR-12); use-credentials only for the learner-voice route on api.

4.4.4 Source selection. (1) If forone-media-v1 holds the full episode.m4a for this manifest version: main.src = URL.createObjectURL(await (await cache.match(url)).blob()) (source: "blob"; the Blob URL is kept for the episode's lifetime and revoked on switch episode; clip shares it). (2) Else if manifest.timing_quality == "word" and the app file exists on the server: main.src = the presigned URL the media route redirects to (source: "network"; ADR-12: show audio is sse_kms_env and served from S3 or the CDN, with Range for seeking), and the page starts the warm (4.6 rule 1) of the full file in the background so the next open is case 1. This is the common path on a morning when the SW warm did not run and the one the 2 s budget is sized on (section 6). (3) Else (streaming): main.src = scene-{s0}, aux.src = scene-{s1} preloaded (presigned scene URLs from episode.manifest); on main.ended swap roles at the seam (the pipeline guarantees a sting or beat at every segment end); when episode.manifest arrives on the stream with the full file, the player switches to it at the next seam, seeking to the same absolute position (segment.start_ms + position). While streaming, only the highlight granularity degrades: sentences[] come from the manifest's sentence-level estimate, data-active moves per sentence, and word taps still resolve through the index. The fold is not changed by streaming: it stays governed by player_defaults.transcript_open, with an explicit override transcript_open: true for kind: pilot (EpisodeCard.transcript_open_override, set by the pipeline's package.json) so A6 shows the transcript with its hint on first contact (PRD 2.2 A6). Under timing_quality: sentence, 🔊 on a word plays the word's sentence, not the word (4.5).

4.4.5 Sync loop. requestAnimationFrame while playing (and a 250 ms setInterval when the tab is hidden, which iOS throttles but does not stop for playing audio): t = main.currentTime * 1000 + scene_offset; binary search words for the active word; if it changed, move the data-active attribute (one DOM write) and, when the active line changes, scroll the transcript so the current line sits at 40% of the viewport (scrollIntoView({block: "center"}) only when the learner has not scrolled in the last 3 s). Word spans are rendered once; nothing re-renders per frame.

4.5 The word sheet

Tap on a word span → index.script.get(line_id).get(i) → gloss_ref → index.glosses[gloss_ref] → render {meaning_native, pos, register_note_native, example_target} plus the sentence the word came from (sentences[] by sent_id) → measure word_sheet_open_ms from pointerup to first paint (PerformanceObserver on the sheet's element-timing), logged in client_perf when it exceeds 300 ms. 🔊 → clip.src = main.src (the same Blob URL or presigned URL), clip.currentTime = (w.s - 60) / 1000, play, pause at w.e + 60 ms (a timeupdate guard plus a setTimeout at the expected duration). When the manifest has only sentence-level timing (timing_quality: sentence, every streaming kind until the republish), the word has no [s, e] of its own: 🔊 plays the sentence that contains it (sentence.s to sentence.e) and the sheet says so in one word ("sentence"); the gloss and Keep are unchanged. Keep → keep {unit_id, sense_key, sentence_text} and an optimistic tick. The sheet is a bottom sheet that does not pause the main audio unless 🔊 is tapped (then main pauses for the clip and resumes).

Phrase selection: pointerdown on a word, pointermove across spans (with touch-action: pan-y so vertical scroll still works), pointerup → the span [i, j] within one line; if any index entry in the span carries a chunk_id whose extent equals [i, j], show the chunk's gloss (index.glosses[chunk gloss_ref]); otherwise show the per-word glosses stacked in order and log one tap per word with chunk: false. A 350 ms long-press on a single word selects it for the drag (iOS otherwise opens the text-selection UI; the transcript has user-select: none).

Misses: when index.missing[] contains the lemma, the sheet shows the sentence at once and calls GET /v1/gloss?lemma=&sense_key= (the pipeline's gloss-service.lookup) with a 1.5 s timeout and a plain "no meaning yet" fallback; this is the only network path on tap and it is rare.

Rules the page enforces on top:

  1. Warm today's episode, in three places, all through one warm(episode_id, manifest_version) function in lib/media/ that is also bundled into the SW: (a) the SW's push handler, on a kind: drop payload carrying episode_id and manifest_version: event.waitUntil(warm(...).then(showNotification)); this is the warm that matters, because tomorrow's episode is normally produced overnight after the pick and becomes ready while the app is closed, and both Chrome and iOS run the push handler with the app closed; (b) the page, on today.changed {reason: episode_ready|extra_ready} while it is in the foreground and on session_closed the evening before (the pipeline publishes to the app the moment the episode is ready; the drop time only controls feed and push); (c) the page, after a Play that streamed (4.4.4 case 2), so the next open is case 1. warm fetches each asset's /v1/episodes/{id}/media/{asset} URL (following the 302 to the presigned URL, ADR-12), checks response.ok and a full Content-Length, and cache.put()s it under the stable /v1 URL into forone-media-v1; the set is web.sw.warm_assets (episode.m4a, timings.json, glosses.json, package.json, article.m4a, recap.m4a, the cover); on a metered connection (navigator.connection.saveData, read in the SW too) only web.sw.warm_assets_metered (the JSON assets) are warmed and the audio streams. The warm is best effort: no push permission, saveData, an evicted SW or a reinstall all leave the cache cold, which is why the cold path is the sized one (section 6) and why play_start_ms carries source. web.sw.cache_episodes_n = 3 keeps today's and the last two; older entries are evicted by the plugin and the archive streams them on demand. Playback reads the cached entries through caches.match() and Blob URLs (4.4.4), so playback never depends on the SW's fetch handler being invoked for a media element, which Safari has historically done inconsistently.
  2. Never cache a partial response. A 206 from api is passed through and not stored (the plugin would otherwise store a truncated body).
  3. Quota. navigator.storage.estimate() on app start; under 100 MB free, cache_episodes_n drops to 1; persist() is requested once after install (granted automatically to installed PWAs on Chrome; iOS ignores it but exempts home-screen apps from the 7-day eviction).
  4. Versioning and deferred activation. Cache names carry a version; a new SW deletes caches with other versions on activate, and activate is deferred: the page listens for updatefound, and messages the waiting SW {type: "activate"} only when PlayerStore is idle, paused or ended and no call or recording is active, then reloads; until then the previous SW and its precache keep serving, so an open page can still lazy-load a route chunk after a deploy (the post-deploy chunk 404 never happens mid-playback or mid-call). Media keys are immutable per (episode_id, manifest_version) so a cached episode survives SW upgrades within a version; a republished manifest (streaming → word timings) changes the key and the page re-adds.
  5. Push and notification click (4.8) live in the same SW, together with the warm of rule 1(a).
  6. Background Sync (forone-events) on Chrome replays the event queue when the page is closed; Safari has no Background Sync, so the queue is replayed on the next open (the 24 h window matches the data domain's clock-skew rule for replays).

The event queue (lib/events/queue.ts): IndexedDB database forone-queue, store batches keyed by batch_id, each a JSON array of EventIn. enqueue(event) buffers in memory for 2 s or 50 events, writes the batch, and posts it; on success the batch is deleted; on network failure it stays; on 4xx other than 429 the batch is marked rejected and reported to Sentry without payload text. Replays send X-Forone-Replay: 1. Batches older than events.queue_ttl_h = 24 are dropped and counted. occurred_at is the device clock at the moment of the event; the server corrects skew.

EpisodeMemory (IndexedDB forone-memory, store episodes keyed by episode_id): {position_ms, speed, transcript_opened_before, article_depth, last_opened_at}; written on pause, seek and every 5 s while playing; mirrored to the server through POST /v1/sessions/{id}/doors/{door} on pause and visibilitychange so the position survives a reinstall (PRD 4 rule 4).

  1. Pre-account.   3. Email code. POST /auth/otp/request always returns 202; rate limits: 3 per email per 10 min, 10 per IP hash per hour; the email is kind signin_code with the 6-digit code and nothing else; verify allows 5 attempts per code; the code is consumed on success.
  4. Apple. Services ID for app.forone.app, response_mode=form_post to /v1/auth/apple/callback, the state cookie carries the pre-account session id; Apple's private relay address is stored as accounts.email. Two practical requirements the week-3 checklist carries: the Apple Developer Program membership (section 10), and registering forone.app and show@forone.app under "Sign in with Apple for Email Communication" with SPF and DKIM on the sending domain, because mail to @privaterelay.appleid.com from an unregistered sender bounces, which would silently break sign-in codes, receipts and the export link for every Apple-relay learner.
  5. Google. OIDC authorization code with PKCE, prompt=select_account; the Google Cloud OAuth consent screen must be verified for forone.app (section 10).
  6. Sessions. Full sessions last auth.session_days = 90, rolling on use; signout revokes the row; account deletion revokes every row at once (data domain 4.12.2 step 1); api sets forone.learner_id for RLS from the row on every request.
  7. Install handoff (D10). The manifest route is a Next.js route handler on app.forone.app: it reads forone_s (same-origin, so the browser sends it with the manifest fetch), forwards it to POST /v1/handoff/mint (one token per learner per 7 days), and returns the manifest JSON with start_url: "/today?h=<token>", scope: "/", display: "standalone", id: "/", icons, theme_color from the show colour, lang and dir from the UI bundle, with Cache-Control: no-store, private and Vary: Cookie so neither the browser nor Vercel's edge serves one learner's manifest to another. A used or expired token with no cookie simply shows the sign-in screen (no email prefilled, no leak). Android Chrome shares the jar, so the token is unused there and expires.

4.11 Bidirectional text

  • <html lang dir> is set once per load from the cached UiBundle (GET /v1/package/ui; ADR-02; PRD 13.1 and 13.2): lang is the learner's native_language, dir is the package's direction, so the chrome is RTL only when the native language is RTL (native/ar) and LTR for native/en and the rest; the target language's direction (UiBundle.target_dir, LTR for English) governs the content surfaces. Nothing in apps/web hard-codes a language or a direction; the string bundle is the package's and the one pair that ships in the beta is built through the same mechanism. Tailwind with only logical utilities (ps-, pe-, ms-, me-, start-, end-, text-start); an ESLint rule forbids pl-, pr-, ml-, mr-, left-, right-, text-left, text-right in apps/web.
  • Every block that may contain learner or host text renders through one <Bidi as="p" text={...}/> component that sets dir="auto" and style="unicode-bidi: plaintext"; an inline target-language run inside a native sentence (Salma quoting an English phrase in an Arabic answer) is wrapped in <bdi> by a tiny tokenizer that splits on script runs (the native script versus Latin) so punctuation stays with its run.
  • Fixed-direction surfaces: the transcript, article, captions, host chat bubbles' target-language text, idea lines and the scrub bar take the target language's direction with text-align: start; the chrome around them follows the native direction. Timestamps 2:14 / 7:02 are LTR runs inside <bdi>.
  • Digits: Western (0 to 9) by default, font-variant-numeric: tabular-nums for times and counts; a native package may set digits otherwise [DECISION; section 10 item 5 for the brand call].
