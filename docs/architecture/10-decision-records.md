# Architecture decision records and the cross-domain pass

Domain 10 of the For one technical architecture. Written 2026-11-06 by the "Finish the architecture documentation" thread after reviewing domains 07 to 09 and cross-checking all nine domain documents against each other, against [decisions.md](../product/decisions.md) (Muath's answers of 2026-10-23) and against [concept-v2.md](../archive/concept/concept-v2.md). Each record below is a ruling that two or more documents now follow; the nine documents were revised on the same day to match. Tags as in the other documents: [DECISION] ruled here; [ASSUMPTION] assumed because the sources are silent; [OPEN for Muath] only the owner could settle; on 2026-11-12 ADR-24 decided every one of them, and section 10 now lists only owner actions and measurements.

The one fact behind most records: the nine documents were written on 2026-10-16 and 10-17 against PRD-v2, which encodes the decisions as they stood on 2026-10-10 (one launch pair, Saudi Arabic speakers learning English, SAR prices, a founding year, Salma's correction notes). On 2026-10-23 Muath decided differently on five points and the pilot kit re-dated the schedule. PRD-v2 remains the build spec wherever decisions.md and concept-v2 are silent; where they differ, decisions.md wins, and the PRD-v3 thread is carrying the same changes into the PRD.

## 3. The decision records

Each record: context, the ruling, consequences per domain, and what stays open.

### ADR-01 Source of truth

**Context.** PRD-v2 (2026-10-10) is the build spec every document cites by part number. Muath's answers of 2026-10-23 overruled parts of it; concept-v2 and decisions.md were updated the same day; the PRD was not. **Ruling.** decisions.md wins over concept-v2, which wins over PRD-v2; PRD part numbers stay as citations for the unchanged parts; where a document cites a changed part it now cites the decision. **Consequences.** Every document's front matter says "revised 2026-11-06 to the decisions of 2026-10-23"; the PRD-v3 thread is told which parts changed (section 5 lists them).

### ADR-02 Languages as two package kinds

**Context.** `package_ar_en` appears in 02 (gloss language, prompts), 03 (Salma persona, talkback), 06 (`lang="ar"`, RTL), 07 (consent texts, notice, crisis), 08 (`packages/language/ar-en/recognizer.yaml`), 09 (`versions.yaml`). Concept-v2 §7 says the target language is a package that passes the gate and the learner's own language "needs only interface text, glosses, and a recognizer that catches it when the learner switches". **Ruling.** Two package kinds. `packages/languages/<target>/`: episode and call voices, streaming and verbatim recognizers with thresholds, lexicon and frequency list, structure inventory and rules, calibration set, law words and correction phrases, crisis keywords, host prompts, format patterns, the ban list. `packages/native/<lang>/`: interface strings (direction from the package: `dir`), consent texts and the privacy notice, gloss target language, Salma's voice and persona lines, crisis clips and the resources card copy, the talkback language hint. `learners` gains `native_language`, `target_language`, `residence_country`; every brief compiler, prompt loader and TTS request reads the pair from the learner row. The pilot's packages are `lang/en` and `native/ar`; `native/en` is the universal fallback for interface and consent. **Consequences.** 02: gloss cache key already carries `native_lang`; prompts load from `lang/<target>`. 03: Salma's talkback and persona from `native/<lang>`; `talkback_stt.languages = [native, target]` per call. 06: `dir` and `lang` from the native package; the landing page is served per `Accept-Language` with English as the default. 07: ADR-20. 08: the gate per target. 09: `versions.yaml` per package; corpora per language. **Open.** None for the mechanism; which native packages exist at launch depends on whose strings and Salma voice are ready (English and Arabic are certain, ADR-24.20).

**Reconciled 2026-11-06 with the sibling threads.** The engineering handbook (engineering/01-repository-layout.md) already uses `packages/languages/<target>/` with `gate.yaml` inside it, so that is the path; the architecture's earlier `packages/lang/` spelling is dropped. The technical design (technical-design/00-overview.md) chose a per-pair package `packages/language/<pair>/` with `ar-en` first and columns `native_lang` / `target_lang`; this record overrides it: two axes, not pairs (a pair package would multiply content by every native language), `packages/languages/<target>/` plus `packages/native/<lang>/`, and the column names `native_language` and `target_language`. The handbook's `ui_strings/` is the UI part of `packages/native/<lang>/`.

### ADR-03 The language gate as code

**Context.** 08 §4.6 specifies the voice blind test, the 50-call latency test and the 30-clip recognizer test for one pair; 09 §4.2 wraps them as suites; concept-v2 §8 names five checks (voices, learner speech to text, writing, the call, structures) that open a language. **Ruling.** `forone.langgate` (in the `vendor-lab` CLI) runs the five checks for a target language and writes one evidence folder `langgate/<target>/<date>/`; a `lang/<target>/gate.yaml` records the pass with the date and the winners; `vendors.yaml` roles that depend on the target (`episode_tts`, `call_tts`, `streaming_stt`, `verbatim_stt`, `pronunciation`) are keyed by target language. Raters: 5 native speakers of the target plus 5 learners of it from anywhere; clips: 30 real learner clips per target. **Consequences.** 08 §4.6 is rewritten as the gate's checks 1, 2 and 4; 09's `recognizers`, `voices-blind` and `calls_50` suites are the gate's regression form; 02's writing check (a native speaker reads 10 scripts) and 04's structure inventory are checks 3 and 5. English runs before launch on the clips of ADR-25.6.

### ADR-04 Plans and allowance

**Ruling.** `plans.yaml`: `one_a_day` $19.99, `two_a_day` $29.99 (recommended; the 7-day trial plan), `three_a_day` $44.99, USD, monthly, VAT or sales tax handled by the processor (ADR-21). `subscriptions.plan` takes these three values; each subscription keeps the price it started at for as long as it lasts, and a price rise applies to new signups only (ADR-25.10; the founding lock and `founding_locked` are removed). The allowance is `plan.episodes_per_day` new episodes per learner-local day, enforced in `api` (`episodes_today < plan.episodes_per_day`), with one swap a day (PRD 3.6) and unlimited listening, article, chat and round two. **Consequences.** 01: `plans.yaml`, the allowance check, `learners.plan`. 06: the plan picker on day 7, "about $1 a day", the compromise and anchor layout from concept-v2 §8, cancel in one tap. 07: ADR-21. 08: ADR-15. 09: `plan_mix`, `blended_margin`. **Open.** None: ADR-24.5 keeps the three prices with a measured-cost trigger and carries the break-even warning.

### ADR-05 Episodes 2 and 3

**Context.** Law 11 (concept-v2 §5): "One, two or three new episodes a day depending on the plan, each with a clear ending, no autoplay and no feed." The batch pipeline makes one episode for the drop; the on-demand path (swap, return) streams in under 30 s. Typical use is 60%, 50% and 45% of the allowance (concept-v2 §8). **Ruling.** Episode 1 is the drop (batch). Episodes 2 and 3 are made when the learner asks ("next one" on Today after the current session's episode is heard), through the on-demand path with `episode_kind = daily_extra`, standard pricing, scene 1 first. The nightly teacher run plans all of the day's episodes (one plan with 1 to 3 episode briefs, each with its own targets so the day's language load stays within the 2 to 4 words and 1 structure per episode rule), so the on-demand run starts at the writer. Learners whose last 7 days show 5 or more extra episodes get episode 2 pre-produced in the nightly batch (`prewrite_extra`), the way 02 D15 pre-writes the rank-2 idea. The feed carries only the drop episode plus any extra the learner has played. **Consequences.** 01: `day/next` creates up to `episodes_per_day` `episodes` rows in state `planned`; `POST /v1/episodes/next`. 02: `daily_extra` kind; the teacher's multi-episode plan schema; `prewrite_extra`. 06: the "next one" control (one button, after the episode ends, never autoplay); the Show tab lists all of the day's episodes. 08: the cost model prices a learner-day as 1 + extras × on-demand premium (about +$0.05 an episode for standard pricing), and the margin by plan uses measured extras.

### ADR-06 Invisible teaching

**Context.** decisions.md §3 drops "the after-call correction notes, the polish card, the chat margin note"; concept-v2 law 7 forbids "the correct answer is" and correction notes; Salma "never corrects, never sends notes". 05 built `notes`, `margin_notes`, a 90-second stage 1, the polish TTS, the notes door; 06 renders them; 08 prices them; 09 measures them; 07 guards them. **Ruling.** Remove: `notes`, `margin_notes` tables and functions; `session/after-pass` stage 1; the notes door and the margin chip; `notes.enabled`; `notes_late`, `chat_opener_late` stays; the "Notes under 90 s" budget; the cost line "Salma's notes and chat" becomes "Salma (when asked) and chat". Keep as evidence (decision 4): the notebook with its "working on" list, "words you own", the tape, "how we know"; the weekly proof and finale through the claim gate; "why this episode"; "where do I stand" when asked, with a range; the "New for you" card from `did_it` and `first_ever` claims; "say it once" and shadowing as pronunciation with internal scoring only. Add: the correction guard in `guard.check_output` (07) with a per-language phrase list, counted in `moves.violations` and in 09's `explicit_corrections_per_100_turns` (ceiling 0); the editor's check "nothing reads as a correction or a lesson" as a model check on every script, article and chat opener (02 check 10 widened); the teacher's "echo plan" (which of the learner's recurring errors the host should recast this call and which right forms the next episodes carry), already the host brief's `recasts` field in 03, now the only correction channel. The after-session pass is one function with the 10-minute budget; the analyst's first stage runs inside it. **Consequences.** 02, 03, 05, 06, 07, 08, 09 revised; the technical-design thread should drop the notes screens and the margin chip. Salma's remaining per-session role is explanations when the learner asks (`salma_explain`, Sonnet, on demand).

### ADR-08 Home region

**Context.** 01 D8 chose `me-central-1` for Saudi residents' data; 07 D7 accepted it; 01 §10 #1 asked counsel "may Saudi residents' voice rest in the UAE or EU". With learners anywhere the question is different: EU and UK learners' data in the UAE is a transfer without an adequacy decision; the same data in Frankfurt needs only the AWS DPA, while the US vendor transfers are the same in every option. Latency does not decide it: 01 §3.6 already lets `call-worker` run near the vendors and no database sits on the turn path. **Ruling.** The default becomes `HOME_REGION = eu-central-1`; `me-central-1` stays available as the alternative if counsel and the first cohort's residence countries favour it; Vercel region follows (`fra1`); Inngest and Langfuse stay EU. The architecture is indifferent between the two AWS regions (one config key), so the choice can be made as late as the Terraform apply in build week 1. **Open.** None since 2026-11-12: ADR-24.8 makes `eu-central-1` final for the beta, and 24.B13 sets the transfer basis (SCCs with a transfer impact assessment, never consent); no counsel step (ADR-25.3); the self-review covers it (register A4).

### ADR-09 Tracing data

**Ruling.** 01 D15 as revised on 2026-10-17 stands for every domain (see the table). 08 D3 and §4.3 are rewritten; 07's Langfuse register row says "metadata and pseudonymous ids by default; pseudonymized, de-identified text only for `data_use` learners; 30 days"; 09 §4.9's Langfuse row says the same. ### ADR-25 Direction change: an AI agent builds it, no dates, no lawyer, web only, no pilot or beta (2026-11-12)

**Context.** After ADR-24, Muath set five constraints: dates no longer matter and none are kept; the product is built by an AI coding agent, not a team of engineers; there is no lawyer; the product is a web application only, with no mobile app; and there is no pilot and no beta.
