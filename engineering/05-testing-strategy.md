# 05. Testing strategy

Part of the For one engineering handbook. Written 2026-11-06 against architecture 09 §4.2 and §4.3, 03 §4.15, 08 §4.6, the coverage checker from the Milestone 0 kit (`milestone-0/tools/coverage-checker.html`, background only) and the known finding that speech-to-text smooths learner errors. Revised 2026-11-12 for ADR-25: tests come first, and the golden sets come from synthetic learners and open clips instead of Milestone 0 (ADR-25.6).

## 1. Tests first

Every story's acceptance criteria are written as automated tests before the code (ADR-25.2). Each test is named for the criterion it proves (`test_e05_s03_ac2_recast_once_per_turn`), the failing tests are the first commit of the branch, and the PR lists them by name under "How tested". A criterion that cannot be automated ("sounds natural") becomes an eval check with a threshold (section 6) or, for voice, a rated blind test (section 5); the PR says which. The review pass fails a PR in which a criterion has no named test.

## 2. What we are testing for

Most products test that code does what the code says. For one also has to test that **a model did what the show's laws say**, every time a prompt, a model, a rule or a vendor changes, and that **the system heard what the learner actually said**. So there are five layers, and only the first two are the ordinary ones.

| Layer | Question | Runs | Cost |
|---|---|---|---|
| Unit | does the code do what it says? | every PR, locally | free |
| Contract and integration | do the services, the database, the queue and the vendors agree on the shapes? | every PR, locally with compose | free |
| End to end | can a synthetic learner live one full day? | staging, nightly and on demand | cents |
| Audio and voice | does the call sound and behave as designed, within the latency budgets, and is the transcript verbatim? | staging, weekly and on vendor change | dollars |
| Model output evals | did the prompt or model change make the show better or worse, against golden sets? | eval-gate on PR, nightly in full | cents to $12 per suite |

## 3. Unit tests

`pytest` per package, fake vendors always. What is worth a unit test here, in order of value:

1. **The guards.** The AI-disclosure guard, the law-word scan, the three-refusals rule, `listener_said()` sanitization, the output guard before any synthesis or send. Each has a table-driven test with Arabic and English cases, and every incident that reaches the guard later adds a row.
2. **The governor** in the call worker: the move contract as a state machine with every budget, tested with scripted move headers.
3. **Coverage** (section 8), fitting, the claim gate, the measures SQL (tested against a fixture database with known answers).
4. **Keys and deletion**: DEK wrap and unwrap, the per-call key derivation, the 15-minute window arithmetic, the retention rules as pure functions of timestamps.
5. **Events**: every event model round-trips; no model has a forbidden field; `events.append()` refuses an update.
6. **Messaging**: exactly three senders and eight transactional kinds; any other caller fails.

Pyright strict on the packages that handle learner data is itself a test. Coverage is reported, not gated.

## 4. Contract and integration tests

Run on every PR against docker compose in the runner (handbook 04 §3).

- **The RLS walk.** For every learner-scoped table and every database role, a session with `SET LOCAL app.learner_id` to learner A reads zero rows of learner B. The test enumerates tables from the schema so a new table is covered the day it is added, and fails if a learner-scoped table has no policy.
- **Migrations** up and down on a fresh database; `migrate-check` for additive-only.
- **Inngest payloads**: no event model carries text, quotes, transcripts or audio (the processor rule for Inngest Cloud).
- **API contract**: the OpenAPI document generated by FastAPI is committed; the `web` client is generated from it; a change to the document without a client regeneration fails the build, and a breaking change needs the `api-breaking` label (the installed PWA may run yesterday's build for a day).
- **Adapter contracts.** Every real adapter is tested against a recorded cassette and the fake adapter is tested against the same cassette: both must produce the same `UnitUsage`, the same priced cost, and satisfy the capability `Protocol`. This is what keeps the fakes honest.
- **Vendor live contract** (nightly, not PR): one minimal real call per wired vendor through the middleware, asserting the response shape, the usage fields the vendor reports, and `health()`. A vendor that silently changes its usage reporting is caught here before it corrupts `vendor_calls`.
- **Privacy jobs**: `audio/expire`, `learner/purge-audio`, `learner/delete` and `privacy/verify` run against MinIO and compose Postgres with the clock mocked; the test proves the verify job catches a doer that was deliberately broken.

## 5. End to end: a synthetic learner's day

`tools/e2e day` on staging runs the whole loop for one synthetic learner with real vendors: `day/next` fires, the idea is chosen, `episode/produce` runs through teacher, writer, fitter, editor, voice studio; the drop publishes; the player streams the episode; the scripted caller holds a call through `call-bench`; the after-pass completes (one function, p95 under 10 minutes; there are no notes, ADR-06); the notebook updates; the measures job computes the day. Assertions are on rows and timings, never on the content of the episode (that is the evals' job). It runs nightly and before every prod release as part of the canary (a shortened version).

Playwright drives the web app for the ten smoke flows against a mocked API on every PR, and against staging in the nightly. Mobile Safari is in the nightly matrix because the PWA target is a phone.

## 6. Audio and voice testing

This is where this product is unusual.

**Verbatim first.** Streaming speech-to-text smooths learner errors: "I go yesterday" comes back as "I went yesterday". Every test that touches learner speech therefore has two truths: the streaming transcript (what the host heard, for the conversation) and the verbatim transcript (what the learner said, for the evidence). The `recognizers` suite scores both against **hand-written verbatim transcripts** of the recognizer clips (ADR-25.6: utterances from the open speechocean762 corpus, Apache-2.0, plus about 30 clips recorded by volunteers from at least two native-language groups, each with a one-line consent, register A2), with code-switch and long-pause marks, and the metric that gates a vendor is **error-preservation rate**: of the learner errors the hand transcript marks, how many survive in the vendor's output. Word error rate is reported second. A recognizer with a lower WER that erases the errors is the wrong recognizer.

**The simulated caller.** Each synthetic learner has a caller profile: 20 to 25 scripted turns with planted errors at known positions and pause marks, rendered once to audio by a TTS vendor that is **not** the recognizer under test (so a recognizer never hears its own vendor's synthesis). `tools/call-bench` joins a LiveKit room as the learner, plays the turns with the profile's pauses, records every timing the worker reports, and writes a row per call.

**`calls_50`** (architecture 03 §4.15): 50 scripted calls on staging, generated by the agent from the synthetic learners' caller profiles, weekly in the nightly and on any change to the host prompt, the governor, the call vendors or the worker image. Gates, from PRD 15: end-of-turn to first host audio p50 and p95, talkback answer time, move-contract violations per call (zero tolerated for the hard budgets), talk share, abandoned calls, and the per-call cost. The report is the evidence Muath reads before approving the voice and recognizer choice in `vendors.yaml` (register M2).

**Voice quality** is a human test, not an automated one: `vendor-lab tts` renders the same scripts through every finalist and writes blind rating sheets (the Milestone 0 kit's `blind_pairs.py` is a usable starting point), and Muath and a few volunteer listeners rate them (register A2, ADR-25.6). Automated checks around it: loudness within target, no clipping, sentence timings within 100 ms of the aligner, the character's voice id unchanged (a fingerprint of the first 5 seconds against the committed reference, so a vendor swapping a voice under us is caught by the canary).

**Audio deletion** is tested as a property: after any test call on staging with `voice_storage = false`, the verify job must find zero learner-voice objects older than 15 minutes. The nightly asserts it after `calls_50`.

## 7. Model output evals and golden sets

The offline suite (`forone.eval`, `tools/eval`) is the layer that turns "a change that worsens any of these does not ship" into a CI check. Its parts:

**Golden sets** live in `eval/fixtures/` and come from synthetic learners and calls the agent generates, the open and volunteer recognizer clips, and Muath's own reads (ADR-25.6; handbook 09 §6):

| Set | Contents | Suites |
|---|---|---|
| `learners/` | 40 synthetic learner files at different levels, with planted error patterns, interests and facts | `pipeline`, `teacher` |
| `scripts/` | scripts and articles with Muath's hand-checked coverage, new words and level | `fitter` |
| `editor/` | packages with Muath's read and the AI review pass's flags, plus the editor's verdict at the time | `editor` |
| `transcripts/` | scripted call transcripts with error tags, structure ids and "blurred meaning" marks | `analyst`, `host` replay |
| `clips/recognizer/` | speechocean762 utterances and the consented volunteer clips, with verbatim hand transcripts | `recognizers` |
| `recordings/` | synthetic then-and-now pairs with known differences; real pairs only after launch, from opted-in learners | `rater` |
| `facts/` | confirmed and rejected life-fact candidates with quotes, plus every wrong-memory case from production | `memory` |
| `similarity/` | scripts judged too alike | `writer`, `editor` |
| `injection/` | prompt-injection and jailbreak attempts in Arabic and English, with the expected behaviour | `injection` |
| `pii_corpus.jsonl` | 300 lines of every PII shape in both languages | `pii_scrub` |

**Checks** are functions in `forone.eval.checks` returning named metrics. Three kinds: **code checks** (coverage, length, banned words, law words, schema validity, fact provenance: does every fact in the script trace to a confirmed fact in the brief), **model-judged checks** (a judge model from a different vendor than the writer scores the script on a rubric with Muath's reads of a sample as the calibration set; the judge's agreement with the humans is itself a reported metric and a judge below 0.7 agreement cannot gate), and **replay checks** (the host prompt replayed over the scripted transcripts; the governor's verdict on each move).

**Thresholds** in `eval/thresholds.yaml`: a floor or ceiling per metric (absolute) and `max_regression` against the committed baseline. The first baselines are the first passing runs on the synthetic sets, with the coverage targets from the PRD and the editor's agreement with Muath's reads. Raising a threshold needs a reason in the PR; lowering one needs Muath's approval.

**The gate.** Handbook 04 §3: the diff decides the suites, the cost is printed first, a breach fails, the run id travels into the release manifest. What the gate cannot catch, the nightly and the episode review catch: after launch, an AI review pass reads a sample of shipped episodes against the laws and ban lists and Muath spot-checks its flags (ADR-25.7); the flags flow back into `editor/` fixtures monthly, so the golden set grows from production.

**Determinism.** Model outputs vary. Every model-judged metric is computed over the whole set with the judge at temperature 0, and the threshold has a tolerance derived from three baseline runs (the standard deviation is stored next to the baseline). A metric whose run-to-run noise exceeds its allowed regression is marked `advisory` and reported but cannot fail the gate until its noise is reduced (more fixtures or a better check).

## 8. The coverage checker: from the kit to the code

`milestone-0/tools/coverage-checker.html` is a single-page tool Muath built for the Milestone 0 kit: paste a script, give the learner's vocabulary estimate and the planned new words, and it reports whether 95% of the script (98% of the article) is known words, flagging the sentences that are not. It is the oldest working piece of For one and the first thing to port.

Port plan (phase 1):

1. Extract its word-frequency list and lemmatization into `forone.pipeline.coverage` with the same inputs (`script`, `vocab_estimate`, `new_words`) and the same outputs (`known_share`, `flagged_sentences`, `unknown_words`), using `wordfreq` and spaCy lemmas instead of the page's own tables, and commit the page's tables as a fixture.
2. Run both over every script in `eval/fixtures/scripts/` (the synthetic set plus the kit's sample scripts) and assert the Python port agrees with the page within one percentage point and flags the same sentences. Where they disagree, Muath's hand check in the fixture decides which is right, and the port is fixed, not the fixture.
3. Make the page itself a test oracle: the `fitter` suite's `coverage_hand` metric is exactly the page's number, so the first baseline for the fitter is the page.
4. Keep the HTML page in the repo as a reference and as the human's second opinion; it is not maintained further.

Everything the fitter does beyond coverage (choosing which new words, deciding when to send a sentence back to the writer, at most two rounds) is tested the same way: against Muath's hand decisions on a sample of scripts as the golden set.

## 9. What is not tested, on purpose

- Pixel-perfect UI across browsers. The smoke flows and Muath's look at the Vercel preview on a phone are enough at launch.
- The episode's **quality** by automated checks alone; after launch the AI review pass reads a monthly sample per learner and Muath reads its flags, and that is the real test (ADR-25.7).
- Load beyond 20 concurrent calls before launch; `call-bench --concurrency 20` runs once in the call phase and again before launch, and the concurrency test is raised when signups approach it.
- Anything against prod data. There is no test data in prod except the one synthetic canary learner.
- A paid penetration test, at launch (ADR-25.11). Security is tested instead by dependency and secret scanning in CI, the OWASP ZAP baseline scan of staging in the nightly, the RLS walk, the privacy-job tests, and the AI security review of every change to auth, keys, media URLs, the feed or deletion (handbook 04 §3). A paid test becomes necessary at 1,000 paying learners, before any B2B contract, or after any security incident.
