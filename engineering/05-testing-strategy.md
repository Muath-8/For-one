# 05. Testing strategy

Part of the For one engineering handbook. Written 2026-11-06 against architecture 09 §4.2 and §4.3, 03 §4.15, 08 §4.6, the Milestone 0 kit (04-production.md, tools/coverage-checker.html) and the known finding that speech-to-text smooths learner errors.

## 1. What we are testing for

Most products test that code does what the code says. For one also has to test that **a model did what the show's laws say**, every time a prompt, a model, a rule or a vendor changes, and that **the system heard what the learner actually said**. So there are five layers, and only the first two are the ordinary ones.

| Layer | Question | Runs | Cost |
|---|---|---|---|
| Unit | does the code do what it says? | every PR, laptop | free |
| Contract and integration | do the services, the database, the queue and the vendors agree on the shapes? | every PR, laptop with compose | free |
| End to end | can a synthetic learner live one full day? | staging, nightly and on demand | cents |
| Audio and voice | does the call sound and behave as designed, within the latency budgets, and is the transcript verbatim? | staging, weekly and on vendor change | dollars |
| Model output evals | did the prompt or model change make the show better or worse, against golden sets? | eval-gate on PR, nightly in full | cents to $12 per suite |

## 2. Unit tests

`pytest` per package, fake vendors always. What is worth a unit test here, in order of value:

1. **The guards.** The AI-disclosure guard, the law-word scan, the three-refusals rule, `listener_said()` sanitization, the output guard before any synthesis or send. Each has a table-driven test with Arabic and English cases, and every incident that reaches the guard later adds a row.
2. **The governor** in the call worker: the move contract as a state machine with every budget, tested with scripted move headers.
3. **Coverage** (section 7), fitting, the claim gate, the measures SQL (tested against a fixture database with known answers).
4. **Keys and deletion**: DEK wrap and unwrap, the per-call key derivation, the 15-minute window arithmetic, the retention rules as pure functions of timestamps.
5. **Events**: every event model round-trips; no model has a forbidden field; `events.append()` refuses an update.
6. **Messaging**: exactly three senders and eight transactional kinds; any other caller fails.

Pyright strict on the packages that handle learner data is itself a test. Coverage is reported, not gated.

## 3. Contract and integration tests

Run on every PR against docker compose in the runner (handbook 04 §3).

- **The RLS walk.** For every learner-scoped table and every database role, a session with `SET LOCAL app.learner_id` to learner A reads zero rows of learner B. The test enumerates tables from the schema so a new table is covered the day it is added, and fails if a learner-scoped table has no policy.
- **Migrations** up and down on a fresh database; `migrate-check` for additive-only.
- **Inngest payloads**: no event model carries text, quotes, transcripts or audio (the processor rule for Inngest Cloud).
- **API contract**: the OpenAPI document generated by FastAPI is committed; the `web` client is generated from it; a change to the document without a client regeneration fails the build, and a breaking change needs the `api-breaking` label (the installed PWA may run yesterday's build for a day).
- **Adapter contracts.** Every real adapter is tested against a recorded cassette and the fake adapter is tested against the same cassette: both must produce the same `UnitUsage`, the same priced cost, and satisfy the capability `Protocol`. This is what keeps the fakes honest.
- **Vendor live contract** (nightly, not PR): one minimal real call per wired vendor through the middleware, asserting the response shape, the usage fields the vendor reports, and `health()`. A vendor that silently changes its usage reporting is caught here before it corrupts `vendor_calls`.
- **Privacy jobs**: `audio/expire`, `learner/purge-audio`, `learner/delete` and `privacy/verify` run against MinIO and compose Postgres with the clock mocked; the test proves the verify job catches a doer that was deliberately broken.

## 4. End to end: a synthetic learner's day

`tools/e2e day` on staging runs the whole loop for one synthetic learner with real vendors: `day/next` fires, the idea is chosen, `episode/produce` runs through teacher, writer, fitter, editor, voice studio; the drop publishes; the player streams the episode; the scripted caller holds a call through `call-bench`; the after-pass makes notes within 90 seconds; the notebook updates; the measures job computes the day. Assertions are on rows and timings, never on the content of the episode (that is the evals' job). It runs nightly and before every prod release as part of the canary (a shortened version).

Playwright drives the web app for the ten smoke flows against a mocked API on every PR, and against staging in the nightly. Mobile Safari is in the nightly matrix because the PWA target is a phone.

## 5. Audio and voice testing

This is where this product is unusual and where the Milestone 0 findings bite.

**Verbatim first.** Streaming speech-to-text smooths learner errors: "I go yesterday" comes back as "I went yesterday". Every test that touches learner speech therefore has two truths: the streaming transcript (what the host heard, for the conversation) and the verbatim transcript (what the learner said, for the evidence). The `recognizers` suite scores both against **hand-written verbatim transcripts** of the 30 consented clips, with code-switch and long-pause marks, and the metric that gates a vendor is **error-preservation rate**: of the learner errors the hand transcript marks, how many survive in the vendor's output. Word error rate is reported second. A recognizer with a lower WER that erases the errors is the wrong recognizer.

**The simulated caller.** Each synthetic learner has a caller profile: 20 to 25 scripted turns with planted errors at known positions and pause marks, rendered once to audio by a TTS vendor that is **not** the recognizer under test (so a recognizer never hears its own vendor's synthesis). `tools/call-bench` joins a LiveKit room as the learner, plays the turns with the profile's pauses, records every timing the worker reports, and writes a row per call.

**`calls_50`** (architecture 03 §4.15): 50 scripted calls on staging, weekly in the nightly and on any change to the host prompt, the governor, the call vendors or the worker image. Gates, from PRD 15: end-of-turn to first host audio p50 and p95, talkback answer time, move-contract violations per call (zero tolerated for the hard budgets), talk share, abandoned calls, and the per-call cost. The report is the evidence Muath signs for the voice and recognizer decisions on 2026-11-08 and 2026-11-13.

**Voice quality** is a human test, not an automated one: the blind pairs tool in `milestone-0/tools/blind_pairs.py` is the starting point for the rater sheets; `vendor-lab tts` renders the same scripts through every finalist and writes the sheets. Automated checks around it: loudness within target, no clipping, sentence timings within 100 ms of the aligner, the character's voice id unchanged (a fingerprint of the first 5 seconds against the committed reference, so a vendor swapping a voice under us is caught by the canary).

**Audio deletion** is tested as a property: after any test call on staging with `voice_storage = false`, the verify job must find zero learner-voice objects older than 15 minutes. The nightly asserts it after `calls_50`.

## 6. Model output evals and golden sets

The offline suite (`forone.eval`, `tools/eval`) is the layer that turns "a change that worsens any of these does not ship" into a CI check. Its parts:

**Golden sets** live in `eval/fixtures/` and come from Milestone 0 (handbook 09 §6 on consent) and from synthetic learners:

| Set | Contents | Suites |
|---|---|---|
| `learners/` | 15 pilot learner files, tokenized, plus 25 synthetic ones with planted error patterns | `pipeline`, `teacher` |
| `scripts/` | scripts and articles with Muath's hand-checked coverage, new words and level | `fitter` |
| `editor/` | packages with Muath's read and the reviewer's flags, plus the editor's verdict at the time | `editor` |
| `transcripts/` | call transcripts with error tags, structure ids and "blurred meaning" marks | `analyst`, `host` replay |
| `clips/recognizer/` | the 30 consented clips with verbatim hand transcripts | `recognizers` |
| `recordings/` | then-and-now pairs with blind ratings | `rater` |
| `facts/` | confirmed and rejected life-fact candidates with quotes, plus every wrong-memory case from production | `memory` |
| `notes/` | Salma's notes as sent | `notes`, `law_scan` |
| `similarity/` | scripts judged too alike | `writer`, `editor` |
| `injection/` | prompt-injection and jailbreak attempts in Arabic and English, with the expected behaviour | `injection` |
| `pii_corpus.jsonl` | 300 lines of every PII shape in both languages | `pii_scrub` |

**Checks** are functions in `forone.eval.checks` returning named metrics. Three kinds: **code checks** (coverage, length, banned words, law words, schema validity, fact provenance: does every fact in the script trace to a confirmed fact in the brief), **model-judged checks** (a judge model from a different vendor than the writer scores the script on a rubric with the Milestone 0 human reads as the calibration set; the judge's agreement with the humans is itself a reported metric and a judge below 0.7 agreement cannot gate), and **replay checks** (the host prompt replayed over recorded transcripts; the governor's verdict on each move).

**Thresholds** in `eval/thresholds.yaml`: a floor or ceiling per metric (absolute) and `max_regression` against the committed baseline. The first baselines are the Milestone 0 numbers (the kit's coverage, the editor's agreement with Muath, the hand-tagged error counts). Raising a threshold needs a reason in the PR; lowering one needs Muath.

**The gate.** Handbook 04 §3: the diff decides the suites, the cost is printed first, a breach fails, the run id travels into the release manifest. What the gate cannot catch, the nightly and the human review (architecture 09 §4.5) catch: the reviewer's flags on shipped episodes flow back into `editor/` fixtures monthly, so the golden set grows from production.

**Determinism.** Model outputs vary. Every model-judged metric is computed over the whole set with the judge at temperature 0, and the threshold has a tolerance derived from three baseline runs (the standard deviation is stored next to the baseline). A metric whose run-to-run noise exceeds its allowed regression is marked `advisory` and reported but cannot fail the gate until its noise is reduced (more fixtures or a better check).

## 7. The coverage checker: from the kit to the code

`milestone-0/tools/coverage-checker.html` is a single-page tool Muath used by hand in the pilot: paste a script, give the learner's vocabulary estimate and the planned new words, and it reports whether 95% of the script (98% of the article) is known words, flagging the sentences that are not. It is the oldest working piece of For one and the first thing to port.

Port plan (build week 1):

1. Extract its word-frequency list and lemmatization into `forone.pipeline.coverage` with the same inputs (`script`, `vocab_estimate`, `new_words`) and the same outputs (`known_share`, `flagged_sentences`, `unknown_words`), using `wordfreq` and spaCy lemmas instead of the page's own tables, and commit the page's tables as a fixture.
2. Run both over every pilot script in `eval/fixtures/scripts/` and assert the Python port agrees with the page within one percentage point and flags the same sentences. Where they disagree, Muath's hand check in the fixture decides which is right, and the port is fixed, not the fixture.
3. Make the page itself a test oracle: the `fitter` suite's `coverage_hand` metric is exactly the kit's number, so the first baseline for the fitter is the pilot.
4. Keep the HTML page in the repo as a reference and as the human's second opinion; it is not maintained further.

Everything the fitter does beyond coverage (choosing which new words, deciding when to send a sentence back to the writer, at most two rounds) is tested the same way: against the pilot's hand decisions as the golden set.

## 8. What is not tested, on purpose

- Pixel-perfect UI across browsers. The smoke flows and a weekly look by a person are enough for a beta of 100.
- The episode's **quality** by automated checks alone; the human reviewer reads 10 per learner per month and that is the real test.
- Load beyond 20 concurrent calls until the beta is two weeks old; `call-bench --concurrency 20` runs once in week 4 and again before any invite batch larger than 100.
- Anything against prod data. There is no test data in prod except the one synthetic canary learner.
